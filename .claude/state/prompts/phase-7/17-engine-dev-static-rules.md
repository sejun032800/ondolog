engine-dev 에이전트로 아래 작업을 진행해주세요.

## 목표

지금까지 지시서마다 손으로 깎아온 `grep` 검증 중 셋을, **기존 정적
테스트 스위트에 규칙으로 얹거나 집계 스크립트로 옮긴다.**

## 배경 (읽고 시작할 것)

검증 명령이 `grep`이라 **주석과 실행 코드를 구분하지 못한다.** 지금까지
다섯 번 오탐이 났다 — 금지 식별자를 "쓰지 않는다"고 적은 주석, 참조용
docblock, 문서 인용 등이 매번 걸렸다.

오탐이 반복되면 사람이 그 검사를 건너뛰게 된다. 이 프로젝트에서 이미
한 번 그렇게 죽은 검증이 있었다.

**정적 테스트는 주석을 제거한 뒤 검사할 수 있고, 새 파일이 자동으로
편입된다.** 기존 스위트가 그 성질을 이미 갖고 있다 — 최근 추가된 엔진
파일이 손대지 않고 검증망에 들어왔다.

## 참조

| 대상 | 내용 |
|---|---|
| `__tests__/engine/` 하위 정적 스위트 | 결정론 규칙·import 경계 검사 (이 작업의 이관 대상지) |
| `__tests__/engine/dnaBaseScore.test.ts` | **선례.** 주석 제거 후 식별자를 검사하는 정적 테스트가 여기 있다 |
| `docs/ONDOLOG_MASTER.md` | 규칙의 근거. 절은 아래 각 규칙에 명시 |

## 입력

- 개발 환경: Windows / PowerShell
- 현재 테스트: 348개 통과, `npx tsc --noEmit -p .` 0 에러

## 1부 — 기존 구조 조사 후 보고 (구현 전에 완료할 것)

아래를 조사해 보고한 뒤 구현에 들어간다.

1. `__tests__/engine/` 하위의 **정적 검사 스위트 전부**를 찾아,
   각각 무엇을 어떤 방식으로 검사하는지
2. 그 스위트들이 **검사 대상 파일을 어떻게 수집**하는지
   (디렉터리 순회인지, 목록이 박혀 있는지)
3. **주석 제거 방식**이 이미 구현돼 있는지. 있다면 어느 파일의
   어느 함수인지
4. 선례 테스트(`dnaBaseScore.test.ts`의 양 기반 금지 검사)가
   주석을 어떻게 처리하는지

**주석 제거 유틸이 이미 있으면 그것을 재사용한다.** 새로 만들지 않는다.
없으면 그 사실을 보고하고, 선례 테스트의 방식을 따른다.

**같은 유틸이 여러 파일에 복제돼 있으면 이번 작업에서 추출·통합하지
않는다.** 규칙을 얹는 스위트 안에 이미 있는 것을 그대로 쓴다. 통합은
별도 작업이다 — 통합하면 기존 테스트 여러 개를 건드리게 되고 이번
작업의 위험이 불필요하게 커진다.

## 2부 — 테스트로 얹을 규칙 둘

**기존 스위트에 규칙을 추가한다. 새 테스트 파일을 만들지 않는다.**
파일을 새로 만들면 자동 편입 성질을 다시 만들어야 하고, 그게 이
이관의 목적에 어긋난다.

각 규칙은 **주석을 제거한 뒤** 검사한다.

**문자열 리터럴 제거는 이번 범위가 아니다.** 지금까지의 오탐은 전부
주석이었고, 문자열 리터럴을 제대로 지우려면 파서가 필요하다.

### 파일 수집 — 재귀로 할 것

**규칙 A·B의 검사 대상은 `src/engine/` 하위를 재귀로 수집한다.**

기존 스위트는 `src/engine/` 루트의 `.ts`만 훑는다. 그래서
하위 디렉터리의 파일이 검증망 밖에 있다. 앞으로 코너 생성 코드가
하위 디렉터리에 만들어지면, **규칙 B가 가장 필요한 자리가 검사되지
않는다.**

- `.ts`만 수집한다. `src/engine/data/`의 `.json`은 대상이 아니다
- `.test.ts`는 제외한다
- **기존 규칙의 수집 범위는 건드리지 않는다.** 그건 별개 판단이고,
  넓히면 기존 통과 상태가 깨질 수 있다. 이번에 추가하는 규칙 A·B에만
  재귀 수집을 적용한다

> 재귀로 바꾸면 현재 코드가 규칙 A·B를 통과하는지는 미지수다.
> **통과하지 않으면 그것이 발견이다** — 코드를 고치지 말고 멈추고
> 보고한다.

### 규칙 A — 결정론 금지 식별자

`src/engine/` 하위 실행 코드에 아래가 나타나지 않는다.

```
Math.random
Date.now
new Date
```

근거: 엔진 함수는 동일 입력에 동일 출력을 낸다(절대 규칙 2).

**주석에서 이 이름을 언급하는 것은 위반이 아니다.** 실제로 여러 파일이
"이런 것을 쓰지 않는다"는 설명을 docblock에 갖고 있다.

### 규칙 B — 엔진의 외부 상태 접근 금지

`src/engine/` 하위 실행 코드에서 DB·네트워크·환경변수에 접근하지 않는다.

- `supabase` 클라이언트 import
- `fetch` 호출
- `process.env` 접근

근거: 엔진은 계수와 데이터를 **인자로만** 받는다. 조회는 호출부의
책임이다(MASTER Part 10-7-5, 10-8-3).

**예외**: `src/engine/data/` 아래 커밋된 JSON의 정적 import는 DB·
네트워크·환경변수 어디에도 해당하지 않는다. 다만 **규준집단 파일을
엔진이 직접 import하는 것은 별도로 금지**돼 있으므로(Part 10-8-3),
그 규칙이 기존 스위트에 이미 있는지 1부에서 확인하고 **있으면 중복
추가하지 않는다.**

## 3부 — 집계 스크립트 하나

### `UNRESOLVED` 소비 지점 열거

**이것은 테스트로 만들지 않는다.**

소비 지점은 정상 작업에서 늘어난다. 고정된 수를 assert하면 정상적인
작업이 매번 실패한다. **차단이 아니라 관측이 목적이다.**

`scripts/` 아래에 집계 스크립트를 만들어 아래를 출력한다.

```
정의 지점   : 파일 · 줄번호
소비 지점   : 파일 · 줄번호 · 소비하는 키
합계        : 정의 N + 소비 M
```

- **주석을 제거한 뒤** 세어야 한다
- 파일 목록을 박지 말고 `src/engine/` 하위를 **재귀로** 순회한다
  (`src/engine/constants/unresolved.ts`가 하위 디렉터리에 있으므로
  재귀가 아니면 정의 지점 자체를 놓친다)
- 파일 I/O 없이 stdout에 출력한다
- 실행 방법을 보고에 명시한다

기존 진단 스크립트들과 같은 위치·같은 실행 방식을 따른다.

## 하지 말 것 — 범위 경계

**레지스트리 ↔ MASTER Part 16-2 대조를 정적 테스트로 만들지 않는다.**

문서에 키를 먼저 추가하는 것이 정상 순서다. 테스트로 막으면 그때마다
관계없는 작업이 멈춘다. **그 대조는 `rule-auditor` 감사 항목이며,
경고는 하되 차단하지 않는 층이다.** 이 작업의 범위가 아니다.

**일회성 진단용 검증을 상시 테스트로 만들지 않는다.** 축 수치
(`20/50/85`)나 특정 항 식(`100 -`·`75 -`) 같은 것은 조사 과정에서
쓰인 것이고, 상시 규칙으로 두면 다음 조사를 방해한다.

## 완료 기준

- 1부 조사 결과가 보고됐다
- 규칙 A·B가 **기존 스위트에 추가**됐고 새 테스트 파일이 없다
- 두 규칙 모두 **주석 제거 후** 검사한다 (문자열 리터럴은 범위 밖)
- 규칙 A·B의 파일 수집이 **`src/engine/` 하위 재귀**다
- 기존 규칙의 수집 범위가 변경되지 않았다
- 주석 제거 유틸이 이미 있었다면 **재사용**했고, 복제본을 통합하지 않았다
- 규칙 B가 기존에 이미 있던 검사와 **중복되지 않는다**
- `UNRESOLVED` 집계 스크립트가 존재하고 재실행 가능하며,
  정의·소비를 분리해 출력한다
- 집계 스크립트가 파일 목록을 박지 않고 디렉터리를 **재귀로** 순회한다
- **현재 코드가 규칙 A·B를 전부 통과한다** — 위반이 발견되면
  코드를 고치지 말고 **멈추고 보고한다**
- 기존 테스트 348개 전부 통과 (신규 테스트로 증가하는 것은 정상)
- `npx tsc --noEmit -p .` 통과 (**0 에러**)
- **`src/` 아래에 변경이 없다**
