## 1단계 — 부하 상태로 찾기

- **부하 조건**: Vitest 워커를 **최대**(논리 코어 수)로 + 동시에 **다른 부하**(예: Vitest 전체를 한 벌 더 동시 실행하거나, 코어를 바쁘게 하는 Node 기본 스크립트 — 새 패키지 0). 어떤 부하를 썼는지 보고에 한 줄
- 그 조건에서 **Vitest 전체 20회** → 실패한 시험마다:

| 시험 파일 · 이름 | 실패 횟수 / 20 | 실패 모양(시간 초과 · 단언 · 예외) | 원인 분류 | 근거(파일:줄) |
|---|---|---|---|---|

- 원인 분류는 아래 다섯 가지 중 하나(둘 이상이면 주된 것): **A 실제 시계 · 고정 대기** / **B `waitFor` · 찾기 기본 시간** / **C 전역 상태 새어 나감** / **D 병렬 충돌(같은 자원 · 같은 키 · 같은 포트)** / **E 그 밖**(설명 한 줄)
- 85-에서 실패했던 여섯 곳과 `feedPhotoStage` · 76-j 채팅 머리는 20회에 안 걸려도 **따로 읽어서** 같은 표에 넣음(실패 0이면 "0/20 · 위험 요소 있음/없음")

## 2단계 — 원인별로 고치기

| 분류 | 처리 |
|---|---|
| A 실제 시계 · 고정 대기 | 가짜 타이머(`vi.useFakeTimers`) 또는 시계 주입(76-j · 85- 방식). testing-library `waitFor`와 함께 쓸 때 멈춤이 없게(`shouldAdvanceTime` 또는 명시적 `advanceTimers`) — 고른 방식 한 줄 |
| B 기다리는 시간 | 기본값에 기대지 않고 **명시 상한**. 키운 곳은 이유 한 줄. 가능하면 기다릴 대상을 바꿔서(정확한 요소 · 상태) 시간을 줄이는 쪽 먼저 |
| C 전역 상태 | 공용 setup의 `afterEach`에서 초기화(기기 저장 · 모킹 · 타이머 · DOM). 시험 순서가 바뀌어도 통과하는지 **무작위 순서**로 한 번 확인 |
| D 병렬 충돌 | 파일 단위 격리(고유 키 · 임시 경로 · 포트). 정말 격리가 안 되는 묶음만 그 파일을 순차로 — 몇 개인지 보고 |
| 워커 수 | Vitest(필요하면 Playwright도) 워커 수를 **고정값**으로. 값은 측정으로 고르고(예: 코어의 절반 · 전체 비교) 고른 이유 한 줄 |
