## 1. 먼저 — 원인 판정 (보고 맨 앞)

**RN ↔ 웹 업로드 순서 비교표**를 단계별로 나란히 만든다. 피드 · 채팅 웹 경로도 한 열씩 둔다.

| 단계 | RN 피드 | 웹 피드(지금) | 웹 채팅(성공) |
|---|---|---|---|
| ① 고르기(입구 · 선택기 종류) | | | |
| ② 파일 읽기(File/Blob/URI · 썸네일 만들기) | | | |
| ③ EXIF 촬영일 읽기 | | | |
| ④ 압축 · 크기 조정 | | | |
| ⑤ Storage 버킷 · 경로 규칙 | | | |
| ⑥ 메타데이터 행(표 · 순서 · 실패 시 처리) | | | |
| ⑦ 영속 큐(앱 재실행 뒤 이어 보내기) | | | |

- 각 칸은 **파일:줄**과 한 줄 설명. 웹 피드가 다른 칸에 표시를 한다.
- **실패 지점을 하나로 판정**한다. 썸네일이 빈 것이 같은 원인인지도 판정한다.
- **⑤가 원인이고 Storage 정책(마이그레이션)을 바꿔야만 고쳐지면 멈춘다**(R82-1 ④). 원인과 필요한 변경만 보고한다. 앱 쪽 경로를 RN과 같게 맞춰서 해결되면 그건 범위 안이다.

## 3. 시험 (`*.vitest.ts(x)` · 행동으로)

- 피드 사진 경로가 채팅과 같은 부품을 부르는지(입구 시트 → 고르기 → 읽기 → 업로드)
- 읽기 성공 시 썸네일 표시 · 실패 시 "다시 고르기" 표시
- **EXIF 촬영일이 있는 파일 → 날짜 채움 / 없는 파일 → 지금 날짜**(가짜 EXIF 파일)
- 업로드 경로 · 메타데이터 행이 RN 규칙과 같은지(가짜 클라이언트로 호출 인자 확인)
- 진단 표시가 운영 빌드에서 0
- **자동 시험이 지키는 범위 / 폰에서만 확인되는 범위를 보고에 나눠 쓴다**(R78-4 — 선택기 종류 · 실제 업로드는 폰에서만)
