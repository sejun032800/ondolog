## 2. 설계 — 보고할 것

아래 각 항목에 **무엇을 어디에 어떤 시그니처로** 둘지 적는다.

### 2-1. 코너 모듈의 위치

세 코너의 파일 경로. **`supabase/functions/` 아래**여야 한다(§17-0-0).
`src/engine/`에 LLM 관련 코드를 두지 않는다(정적 규칙 A·B).

### 2-2. 코너마다 두 함수 (§17-0-5-F)

| 함수 | 입력 → 출력 |
|---|---|
| **요청 만들기** | 조립된 입력 → 프롬프트(캐시 지점 포함)·LLM 출력 스키마 |
| **응답 처리** | LLM 응답 + 입력 + 맥락(커플·호의 기간) → `ValidatedContent` 또는 실패 사유 |

**코너 코드는 전송 방식을 몰라야 한다.** 코너 파일에 LLM을 부르거나 기다리는
코드가 있으면 안 된다. 그 경계를 **무엇으로 확인할지**도 함께 제안한다.

선행 검사("재료가 0인가", §17-0-5-D)를 어디에 둘지도 적는다.

### 2-3. 골격 변경

`runCornerPipeline`·`llmClient`를 어떻게 바꾸는지.

- 골격이 코너의 두 함수를 받아 **호출·재시도·예산**을 맡는다
- **프롬프트 캐싱** — 캐시 지점을 코너가 표시하고 `llmClient`가 전달한다
  (§17-0-5-F). `llmClient`만 SDK·엔드포인트를 안다(규칙 C)
- **층 분리 유지** — `llmClient`는 Zod·`FORBIDDEN_KEYS`를 모르고, 골격은 HTTP를
  모른다(§17-0-5-C)
- **예산이 인자로 흘러가지 않는다** — `#13`의 형태 유지

### 2-4. 검사 순서와 `ValidatedContent`가 생기는 자리

§17-0-4·§17-0-4-A의 순서를 따른다.

```
Zod(LLM 출력 스키마) → FORBIDDEN_KEYS(LLM 출력) → ID 해석 → 원문 채우기 → 저장 스키마
```

- **`FORBIDDEN_KEYS`는 LLM 출력에만** 건다(§17-0-4 제목). 파이프라인이 채운
  저장 내용에 걸면 엔진 주입값·원문이 오탐될 수 있다
- **`ValidatedContent`가 어디서 만들어지는가.** 승인된 생성 모듈 목록(상수가 원본)
  안에서만 만들어져야 한다. **검증하지 않고 브랜드를 붙이는 공개 함수를 두지
  않는다**(r25에서 막은 구멍). 목록을 늘려야 하면 그 이유를 적는다

### 2-5. LLM 출력 스키마와 저장 스키마

코너마다 **둘을 따로** 둔다(§17-0-4-A).

- LLM 출력 스키마에는 **원문 텍스트 필드가 없다** — ID 참조만
- 저장 스키마는 CORNER_CONTENT §2·§6·§7 그대로
- **§9-7-2의 길이 상한**이 어느 스키마의 어느 필드에 걸리는지

### 2-6. 명시적 빈 결과 (§17-0-5-D)

코너마다 LLM 출력 스키마가 **"해당 없음"을 어떤 형태로 표현**하는지. 그리고:

- 명시적 빈 결과 → `insufficient_input` (`generation_attempts` ≥ 1)
- 파싱 실패 → `schema_invalid`
- **둘이 섞이지 않는다**는 것을 어떻게 보장하는지

17-1 데이트 아카이브는 호출 후 빈 결과가 없다(§17-0-5-D 표). 그래도 스키마가
빈 결과를 막는 형태인지 허용하는 형태인지 적는다.

### 2-7. ID 해석 (§17-0-4-A)

세 조건 — **존재한다 / 그 커플의 것이다 / 해당 호의 기간 안이다** — 을 어떻게
검사하는지.

**입력에 들어 있다는 것만으로 세 조건을 갈음하지 않는다.** 입력 조립이 잘못돼
다른 커플의 레코드가 섞여 들어와도 걸려야 한다. 입력 레코드에 커플 식별자와
시각을 싣고 **각 조건을 명시적으로** 검사하는 형태를 제안한다.

### 2-8. 규칙 F (§17-0-3)

파일명 basename 검사를 어디에 어떻게 둘지. 수집 범위, 제외할 것(`node_modules`·
빌드 산출물), 합성 입력 테스트 구성.

### 2-9. 테스트

1부 조사의 실현 가능성 결과에 따라 Deno 쪽 테스트를 어디에 둘지. 안 되면 사유와
대안.

## 3. 2부에서 증명해야 할 것 — 설계가 이것을 가능하게 하는지 확인

설계 보고에 **각각을 어떤 테스트로 증명할지** 한 줄씩 적는다.

- 코너 코드에 호출·대기 코드가 없다
- 캐시 지점이 `llmClient` 요청에 실제로 실린다
- **다른 커플의 ID를 참조하면 걸린다** — 두 경우 모두
  - LLM이 입력에 없는 ID를 지어냄
  - 입력에 다른 커플 레코드가 섞여 있고 LLM이 그것을 참조함
- 기간 밖 ID가 걸린다
- 명시적 빈 결과 → `insufficient_input`, 파싱 실패 → `schema_invalid` — 분리
- 원문 텍스트를 LLM이 써서 보내도 저장 내용에 들어가지 않는다
- 규칙 C·D·E가 계속 통과한다. 승인 목록을 바꿨다면 합성 입력도 갱신된다
- 규칙 F — 위반·정상 합성 입력, 그리고 저장소 실제 파일이 통과한다
- 게이트 0 / 0, jest 556 대비 감소 없음
