## 목표

연애 온도를 기저 온도와 활동 변동분으로 나누어 구현한다.
기저 온도는 완전 구현하고, 활동 변동분의 입력은 `UNRESOLVED`를 소비한다.

## 이 작업의 성격 — 앞선 두 작업과 다르다

**기존 파일을 수정하는 작업이다.** `src/engine/temperature.ts`가 이미 존재하며,
Phase 2에서 자리표시자를 포함해 만들어졌다.

작업 시작 전에 아래를 먼저 하라.

1. `src/engine/temperature.ts`의 현재 내용을 전부 읽는다
2. **현재 무엇이 구현돼 있고 무엇이 자리표시자인지 보고한다**
3. 기존 시그니처를 바꿔야 한다면 **바꾸기 전에 그 사실을 보고한다**

기존 구현을 지우고 새로 쓰지 말 것. 살릴 것은 살린다.

## 세 부분으로 나눈다

### ① 기저 온도 — 완전 구현

유형 궁합 매트릭스(Part 10-6-5)를 조회해 기저값을 정한다. 구현할 규칙은
Part 10-7에 전부 있다 — 세 단계 값, 비대칭일 때의 처리, 하한, 그리고
양측 프로파일이 없을 때의 동작.

**매트릭스를 다시 옮겨 적지 말 것.** 이미 코드에 존재하는 궁합 판정
로직·상수를 찾아 재사용한다. 찾지 못하면 멈추고 보고한다.

> `#2`에서 확인된 위험과 같다. 같은 표가 두 벌이 되면 이후에 갈라지고,
> 양쪽 다 결정론적이라 테스트로는 잡히지 않는다.

### ② 활동 변동분 — 식은 구현, 입력은 미확정

Part 10-7의 식을 그대로 구현한다. 분모는 문서가 정한 고정값이다.

다만 **하루치 활동 점수의 정의**(채팅·피드 건수를 몇 점으로 환산하는가)가
아직 미확정이며 `UNRESOLVED` 레지스트리의 `temperature.activityScore`로
등록돼 있다. 그 값을 지어내지 말고 `UNRESOLVED`를 소비한다.

### ③ 결합 — 구현하되 실행 시 throw

기저와 변동분을 합치고 문서가 정한 범위로 clamp한다. ②가 미확정이므로
최종 온도 함수는 호출 시 `UNRESOLVED`가 던지는 에러로 실패한다.
**이것이 규격이 의도한 정상 상태다.**

## 계수는 인자로만 받는다

**엔진 함수는 계수를 인자로만 받는다.** `src/engine/` 하위에서 DB·네트워크·
환경변수에 접근하지 않는다. 계수 조회는 호출부의 책임이다(Part 10-7-5).

`daily_temperature.factors`에 계수 버전을 기록하는 것도 **호출부의 일**이다.
엔진 함수는 계산만 한다. 이 작업에서 DB 쓰기 코드를 만들지 않는다.

## 식별자

Part 10-7-1의 식별자 규칙을 따른다. 일간 지표와 유형 궁합은 **서로 다른
어근**을 쓴다. 한글 라벨이 같다는 이유로 코드에서 같은 이름을 쓰지 않는다.

## 완료 기준

- 기저 온도 함수가 **순수 함수**이며 Part 10-7의 규칙을 전부 반영한다
- 궁합 매트릭스·판정 로직을 재사용했으며 재작성이 없다
- 활동 변동분 함수가 식을 구현하고, 점수 정의는 `UNRESOLVED`를 소비한다
- 최종 온도 함수가 **호출 시 throw**하며, 그것을 기대하는 테스트가 있다
- 기저 온도는 throw 없이 계산되고 값이 검증된다 — 비대칭 처리, 하한,
  프로파일 미비 시 동작 각각에 테스트가 있다
- 계수가 전부 인자로 들어오며 `src/engine/` 안에 하드코딩이 없다
- 기존 테스트 289개 전부 통과
- `npx tsc --noEmit -p .` 통과 (**0 에러**)
- `TEMPERATURE_ENGINE_VERSION`을 올렸다면 그 사실과 근거를 보고한다

## `UNRESOLVED` 건수가 늘어나는 것이 정상이다

지금까지 `grep -rn "UNRESOLVED" src/engine/`은 3건이었다. 이번 작업에서
`temperature.activityScore`가 **처음으로 실제 소비**되므로 건수가 늘어난다.

- 선언 3건은 그대로다 — `unresolved.ts`를 수정하지 않는다
- 소비 지점이 추가되는 것은 위반이 아니라 이 작업의 결과다
- **키를 새로 등록하거나 해소하지 않는다**
