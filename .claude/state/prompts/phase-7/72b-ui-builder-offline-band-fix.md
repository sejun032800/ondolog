## 1. 할 일

| # | 할 일 |
|---|---|
| ① | **끊김 판정 좁히기.** 끊김은 **감싼 실제 `fetch` 호출 자체가 거부(reject)된 경우만**이다. 아래는 모두 끊김이 아니다:<br>· HTTP 상태 코드가 무엇이든 응답을 받은 경우<br>· 응답 뒤의 본문 파싱 오류<br>· 앱 코드에서 난 `TypeError`<br>· `AbortError`(요청 취소)<br>"모든 `TypeError` = 끊김" 판정은 지운다. **판정 위치는 `fetch` 호출을 감싼 바로 그 자리**여야 한다(바깥에서 오류 종류로 짐작하지 않는다) |
| ② | **띠 풀기 확인 요청**(허가 — 조건 그대로)<br>· **띠가 떠 있을 때만** 보낸다. 띠가 없으면 확인 요청 0<br>· 보내는 때: 앱이 앞으로 올 때(AppState `active`) + 띠가 떠 있는 동안 **15초에 한 번 이하**<br>· 대상: **같은 Supabase 주소의 상태 확인 하나.** 사용자 데이터 · 사용자 토큰 0. 메인 세션이 엔드포인트를 고르고 보고한다(§1-1)<br>· **응답을 받으면 상태 코드와 관계없이** 연결된 것이다 → 띠를 내리고 타이머와 AppState 감시를 멈춘다<br>· 확인 요청이 거부되면 띠를 그대로 두고 15초 간격을 지킨다(무한 반복 0 · 겹친 타이머 0)<br>· 화면이 사라질 때 타이머와 AppState 구독을 정리한다 |

| ④ | **`global.fetch` 감싸기 점검**<br>· 거부 오류는 **같은 오류 객체를 그대로 다시 던진다**(새 오류로 감싸거나 메시지 · 타입을 바꾸지 않는다)<br>· 응답 객체는 **받은 것 그대로** 돌려준다(복제 · 읽기 0)<br>· 호출 인자(주소 · 옵션)를 바꾸지 않는다<br>· **확인 요청은 감싸기를 두 번 지나지 않는다**(감싸기 전 원래 `fetch`로 보내거나, 한 번만 지나게 — 방식 보고) |
