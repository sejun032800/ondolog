## 배경 (읽고 시작할 것)

Part 16-2는 표와 코드 레지스트리가 **1:1로 대응한다**고 규정한다. 그런데
문서에 키가 추가돼도 코드 반영이 자동으로 따라오지 않아 어긋난 상태가 됐다.

이 작업은 어긋남을 지금 맞추는 것이다. **특정 키 하나를 넣는 작업이 아니라
표 전체를 대조하는 작업**이다 — 하나만 고치면 같은 일이 다음에 또 벌어진다.

## 참조 문서

| 절 | 내용 |

각 키의 `doc` 열이 가리키는 절은 읽지 않아도 된다. 이 작업은 계수를
해소하는 것이 아니라 **등재 상태를 맞추는 것**이다.

## 1부 — 전수 대조 (구현에 손대기 전에 완료하고 기록할 것)

Part 16-2 표의 모든 행과 `unresolved.ts` 레지스트리의 모든 항목을 대조해
아래 셋으로 나눠 보고한다.

| 분류 | 처리 |
|---|---|
| **양쪽에 있고 내용이 같음** | 손대지 않는다 |
| **표에만 있음** | 레지스트리에 추가한다 |
| **코드에만 있음** | **추가도 삭제도 하지 말고 보고만 한다** |

내용이 다른 경우(같은 키인데 `phase`나 `doc`이 어긋남)도 **보고만 한다.**
표가 원본이지만, 코드가 그 값으로 이미 소비되고 있을 수 있어 사람의
판단이 필요하다.

**보고 후 2부로 넘어간다.** 코드에만 있는 키나 내용 불일치가 발견되면
**그 항목은 건드리지 말고** 나머지만 처리한다.

## 2부 — 표에만 있는 키를 추가

- 표의 `key`·`phase`·`doc`을 **그대로** 옮긴다. 요약하거나 다듬지 않는다
- 기존 항목의 형식을 따른다. 새 형식을 만들지 않는다
- **`UNRESOLVED` 함수의 시그니처·동작·에러 타입을 바꾸지 않는다.**
  이 작업은 레지스트리 데이터만 건드린다
- 키 타입이 레지스트리에서 파생되는 리터럴 유니온이면, 추가된 키가
  자동으로 유니온에 들어가야 한다

### 테스트

추가한 키마다 **값이 아니라 throw를 기대하는 테스트**를 만든다.
기존 키의 테스트와 같은 형식이다.

- 등록 키의 throw와 미등록 키의 throw가 **여전히 다른 에러 타입**인지
  확인한다
- 미등록 키 리터럴이 타입 수준에서 거부되는지 확인한다
  (`@ts-expect-error`)

## `UNRESOLVED(` 호출 건수는 변하지 않는다

```
grep -rn "UNRESOLVED(" src/engine/ --include=*.ts | grep -vE "^[^:]*:[0-9]+:[[:space:]]*\*"
```

현재 **2건**이다 — 정의 1건 + `temperature.activityScore` 소비 1건.

**이 작업 후에도 2건이어야 한다.** 레지스트리에 항목을 추가하는 것은
데이터 등재이지 소비가 아니다. 새 키를 실제로 호출하는 코드를 만들지 않는다.

> 새 키의 소비는 별도 작업이다. 여기서 호출부를 만들면 그 작업의 범위를
> 침범한다.

## 하지 말 것

- **키 하나만 보고 넘어가는 것** — 표 전체를 대조한다
- **코드에만 있는 키를 삭제하는 것** — 소비 중일 수 있다. 보고만 한다
- **내용 불일치를 임의로 맞추는 것** — 보고만 한다
- **`UNRESOLVED` 함수 자체를 수정하는 것** — 레지스트리 데이터만 건드린다
- **새 키를 소비하는 호출부를 만드는 것** — 별도 작업이다
- **계수를 해소하거나 값을 넣는 것**
- 다른 엔진 파일 수정 (`temperature.ts`·`dnaScore.ts`·`leagueStats.ts` 등)
- **기존 테스트의 assertion·기댓값 수정** — 금지. 깨지면 멈추고 보고.
  **신규 테스트 추가는 허용**한다
- **상태 파일의 구조를 재편하거나 기록을 이동·삭제하는 것** — 항목 추가만
- 커밋·푸시, 라이브러리 의존성 추가, 설정 파일 변경
- 문서에 없는 값을 지어내는 것 — 판단이 서지 않으면 **멈추고 물어볼 것**
