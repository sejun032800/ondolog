## 1. 새 큰 틀

### 1-1. 북극성

> **실제 커플 데이터로 만든 첫 호 한 권이 폰에 도착한다.**

MASTER 7-3은 "첫 호 발행이 퍼널 전체의 병목"이라고 한다. 모든 작업의 순서는 **여기까지의 거리**로 정한다.
거리가 먼 작업(자동화·결제·얼굴 인식·하늘)은 잘 만든 것이라도 뒤로 간다.

### 1-2. 다섯 원칙

| # | 원칙 | 뜻 |
|---|---|---|
| 1 | **가장 큰 미지수부터 시험한다** | 첫 미지수는 "AI가 만든 지면이 읽을 만한가"다. 방어층을 더 쌓기 전에 실제 출력을 본다 |
| 2 | **얇게 끝까지, 그다음 두껍게** | 입력 → 생성 → 발행 → 조판 → 열람을 운영자 손으로라도 한 번 끝까지 잇는다. 배치·스케줄·경보는 출시 직전에 붙인다 |
| 3 | **계수는 v0로 정하고 데이터로 고친다** | MVP에 보이는 지표는 PM이 v0 값을 **결정**으로 확정하고 버전을 남긴다. 베타 데이터로 v1을 정한다. 그 밖의 미확정 계수는 `UNRESOLVED` 규격을 그대로 따른다 |
| 4 | **완료 = 실기기 시연** | 마일스톤 완료 기준은 화면 녹화나 실제 산출 파일이다. 시험 통과는 필요조건이지 완료가 아니다 |
| 5 | **운영을 줄인다** | 지시서 하나 = 시연 가능한 결과 하나. 내부 구현 결정은 PM에게 올리지 않는다(§5) |

**판정이 "못 싣겠다"면 M2로 가지 않는다.** 프롬프트를 고쳐 다시 잰다. 이 마일스톤의 존재 이유가 이것이다.

> **r16 개정 — M1을 셋으로 나눈다 (R16-1).** Proteur가 실제 호출을 프롬프트 고도화 뒤로 미루기로 했다.

> | 단계 | 내용 | 상태 |

### M2 — 첫 호 수직 슬라이스 (운영자 수동 운영)

**목표.** 실제 커플 한 쌍(본인 커플 또는 동의한 지인 커플)이 앱에 남긴 기록으로 만든 호 **한 권**이 폰 서재에 꽂히고,

## 9. 유지되는 기술 메모

**얼굴 인식 3단계 구조(출시 후).** 탐지 → 임베딩 → 매칭이며, 매칭은 순수 함수(`src/engine/faceMatch.ts`)다. 라이브러리를 바꿔도
매칭 함수는 유지된다. 절대 규칙 1(특징 벡터 서버 전송·저장 금지)은 어떤 대안을 고르든 그대로다.

**렌더링 규칙(MASTER 9-5).** `print_background=True`, margin `0` + CSS padding, `wait_until='networkidle'`, 파일명 ASCII.
조판 원본은 `CORNER_LAYOUT.md`다 — `DESIGN.md`만 보면 구 규격(17면 2테마)으로 조판된다.

**발행 경로(MASTER §17-0-10, SCHEMA §9-D).**
- 생성과 발행은 다른 행위다.
- 발행 성공은 `fn_publish_issue`가 커밋된 것을 말한다(security invoker, service_role만 호출).
- 미디어 목적지 경로는 입력 조립에서 정한다. 검증된 content는 고치지 않는다.

**하늘(출시 후).** 별은 데이트 기록에만 의존하고 유성은 다정한 말들 엔진에 의존한다. 그래서 나눠서 낼 수 있다(구 11a/11b).
r18 디자인에서 별 크기는 그날 온도(일 배치, M3-3)에 기대므로 별을 당길 때 온도 배치가 선행한다(R18-8).

**앱 UI 구현 메모(r18).** 블러 없이 반투명 면 + 머리카락 선, 숫자 발광은 `textShadow`, 별·시트 그림자는 `boxShadow` 문자열(미지원 기기는 반투명 원 두 겹),
하늘은 `Image` 1장 + `translateY(-viewOffsetPt)`, 그레인은 루트 1회 반복 타일. 상세는 `docs/design/nocturne/canvas/Build.dc.html`.
