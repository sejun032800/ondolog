## Part 1. 서비스 개요

### 1-1. 기본 정보

| 항목 | 내용 |
|---|---|
| 서비스명 | **ONDOLOG** |
| 핵심 서비스 | 커플이 앱에 입력·축적한 데이터(대화, 사진, 데이트 기록, 성격 검사 등)를 AI가 일련의 양식으로 조합해 잡지를 자동 발행하는 앱. 아카이브 + 잡지 발행 결합형 서비스 |
| 소비자층 | 2030 커플 |
| 플랫폼 | 모바일 앱(iOS, Android), 웹 페이지 |
| 개발 단계 | 기획 완료 → 개발 착수 |
| 팀 구성 | 1인 창업 (기획·개발·출시·마케팅) |

### 1-2. 기획 목적

연인 관계에서의 '나'를 이해하고, 커플의 일상 데이터를 하나의 콘텐츠로 전환하는 '잡지'를 발간한다.

데이트를 하며 사진을 찍고, 기념일에 편지를 쓰고, 자기 전 다정한 카톡을 남기는 등, 커플 사이에서 기록을 저장하는 무수한 행위들을 하지만 그 순간 이후 다시 그 기록들을 추억하지 않는다. 특히 다투는 채팅들은 전날의 다정했던 채팅을 순식간에 덮어버린다.

ONDOLOG는 우리 사이의 온도를 유지하게끔 커플들의 기록을 커플만의 콘텐츠로 가공하여 잡지 형식으로 발간함으로써, 연인 관계에 정기적으로 활력을 불어넣는 서비스다.

### 1-3. 앱 정체성

**아카이브 + 연인 SNS**를 베이스로, 그 위에 **매거진 레이어**를 얹는 구조.

코너 열람 범위는 구독 티어(Free/유료)로 결정된다. 코너를 개별 재화로 구매하는 à la carte 구조는 **채택하지 않는다.**

### 1-4. 전환 배경 (Twin.me → ONDOLOG)

선행 프로젝트 Twin.me는 "미러 + 아카이브(자기성찰)" 컨셉으로 시작해 매거진 피벗까지 진행했으나, "결국 이 앱을 사용해서 남는 게 뭐지"라는 질문에 기획자 스스로도 확신을 갖지 못해 중단했다.

ONDOLOG는 "커플의 다정한 기록이 다툼 등으로 휘발된다"는 더 명확하고 검증 가능한 페인포인트에서 출발한 **독립적인 재기획**이다. Twin.me의 기술 자산(추론 엔진, PDF 렌더링 파이프라인, 아키텍처 패턴)은 재활용하되, 제품 컨셉은 계승하지 않는다.

## Part 2. 시장 분석 (Problem)

### 2-1. 페인포인트

연인들은 데이트, 카톡, 편지, 사진 등 관계 속에서 수많은 기록 행위를 하지만, 그 순간이 지나면 다시 꺼내보지 않는다. 특히 다툼 이후의 감정적 채팅은 전날의 다정했던 대화를 순식간에 덮어버리며, 관계의 좋은 기억이 휘발되는 구조적 문제가 존재한다.

### 2-2. 경쟁 서비스 벤치마킹

**비트윈 (VCNC/DLT파트너스, 2011년 출시)**

- 13년간 누적 3,500만 다운로드를 기록한 글로벌 1위 커플 앱
- 채팅 + 사진·동영상·메모 저장 + 기념일 알림 + 공유 캘린더 — 커뮤니케이션·아카이브형
- **2025년 8월 데이터 소실 사고**: 무료 이용자의 채팅 내 사진/영상 보관을 3개월로 제한하는 약관 개정 과정에서 앨범 게시물·프로필 사진 등 대다수 무료 사용자 데이터가 소실. 백업 없이 복구 실패.
  → **"기록을 맡길 수 있는 신뢰"가 깨진 사례.** ONDOLOG의 정기 발행(박제된 아카이브) 컨셉이 이 리스크에 대한 대안 서사가 된다.

**썸원 (SumOne, 모니모니, 2020년 출시)**

- 매일 하나의 질문에 답하고, 양쪽이 답변을 완료해야 서로의 답을 볼 수 있는 질문 기반 커플 다이어리
- 국내 누적 가입자 1,400만 명, DAU 약 130만 명, 글로벌 누적 다운로드 2,000만 건
- **외부 투자 없이 부트스트랩 운영**, 일본·마카오·대만 등 6개국 라이프스타일 1위 이력
- "1년 뒤 다시 꺼내보는 연애의 기록"을 명시적 가치제안으로 내세움

**트렌드 신호**: 2021년 데이터 기준 원조 채팅형 앱(비트윈·러브데이)은 설치자가 각각 21.9%, 34.0% 감소한 반면, 기록·질문 중심의 썸원은 27.7% 증가. **채팅 중심 → 기록 중심으로 시장이 이동 중**이다.

**핵심 시사점**: 썸원은 무투자·1,400만 가입자로 "질문→기록→다시 꺼내보기"만으로 시장을 검증했다. ONDOLOG의 차별점은 "다시 꺼내보기"를 유저가 능동적으로 해야 하는 썸원과 달리, **AI가 능동적으로 편집·발행해서 밀어준다**는 데 있다.

### 2-3. 기존 대안의 한계

| 대안 | 사용 이유 | 구조적 한계 |
|---|---|---|
| 카카오톡 | 이미 쓰는 메신저, 진입장벽 없음 | 다정한 대화와 다툼 대화가 시간순으로 뒤섞임. 재구성/큐레이션 없음 |
| 인스타그램 | 예쁜 순간 공유 | 공개 게시 전제라 사적 기록 부적합. 알고리즘 피드에 묻혀 재열람 불가 |
| 비트윈 | 커플 전용 폐쇄 공간 | 본질은 채팅 로그. 아카이브가 형식화되지 않고 원본 그대로 쌓임. 유실 리스크 |
| 썸원 | 자연스러운 기록 축적 | 질문-답변 단위로 파편화. 유저가 능동적으로 찾아야 함. AI 편집·발행 없음 |
| 다이어리/캘린더 앱 | 개인 기록 습관 | 개인 단위 설계, 커플 데이터 통합 불가 |

**공통 구조적 공백 3가지**

1. **저장은 되지만 재구성은 안 된다** — 모든 대안이 쌓기(archiving)까지만 하고, 의미 있는 형태로 가공해 돌려주지 않는다
2. **능동성이 전적으로 유저에게 있다** — 다시 꺼내보려면 유저가 스크롤하고 검색해야 한다. 정기적으로 "받아보는" 경험이 없다
3. **감정의 노이즈를 걸러내지 못한다** — 다툼 기록과 다정한 기록이 동일 층위로 저장되어 좋은 기억이 나쁜 기억에 묻힌다

### 2-4. 포지셔닝

> 기존 서비스들이 "커플의 데이터 창고"였다면, ONDOLOG는 그 창고에서 AI가 선별·편집해 정기적으로 완성된 콘텐츠를 발행해주는 첫 번째 서비스다.

비트윈·썸원과 직접 경쟁하지 않고 **그 위에 얹히는 레이어**로 포지셔닝 가능하다. (예: "카톡·비트윈에 있는 기록을 잡지로 만들어드립니다" 온보딩)

### 2-5. 시장 규모

**인구 기반 (출처 검증 완료)**

- 19~34세 청년인구: 2022년 1,061만 명(통계청 추계), 2020년 1,050만 명 → 2030년 869만 명 감소 전망(국무조정실 「2021 청년정책백서」) → **2025~2026년 약 950만~980만 명 추산**
- 현재 연애 중 비율: 조사마다 24~35% 편차(듀오 34.8%, 타 조사 24.2%) → **보수적으로 28~30% 적용**

**TAM / SAM**

| 단계 | 정의 | 개인 기준 | 커플 단위 |
|---|---|---|---|
| TAM | 19~34세 청년인구 | 약 950만 명 | — |
| TAM(연애중) | 위 중 현재 연애 중(~30%) | 약 285만 명 | 약 143만 커플 |
| SAM | 자기이해 콘텐츠 관심층(~89%) 필터 | 약 254만 명 | 약 127만 커플 |
| **SAM(지불의사)** | 관심→지불의사 전환(보수적 20~25%) | 약 51만~64만 명 | **약 25만~32만 커플** |

> "89%" 수치는 Z세대(주로 20대) 대상 조사(오픈서베이)로, 30대 후반까지 적용 시 과대추정 가능성 — 참고치로만 사용.

**인접 시장 지표**

- 글로벌 커플 관계 앱 시장: 2024년 약 20억 달러 → 2033년 577억 달러 전망 (CAGR 12.5%)
- 국내 데이팅앱 시장: 2023년 기준 1,859억 원
- Z세대 89%가 MBTI·퍼스널컬러 등 자기이해 도구에 관심
- 2026년 운세·자기이해 콘텐츠 마케팅 트렌드: **"디지털 서비스(앱) + 실물 굿즈 결합"**이 핵심 공식 → ONDOLOG의 디지털 잡지 + 실물 발행물 구조와 부합
- AI 생성 콘텐츠(AIGC) 시장: 2024년 270억 달러, 2025~2034년 연평균 11.6% 성장 전망

### 2-6. 앱 전환율 벤치마크 (업계 실측)

Adapty 2026 State of In-App Subscriptions 기준:

- 설치→체험(트라이얼) 전환율 글로벌 평균 **10.9%**
- 체험→유료 전환 평균 **25.6%**
- 카테고리별: 건강·피트니스 35.0%(최고), 엔터테인먼트 19.1%(최저) → ONDOLOG는 중간~상위권(25~30%) 목표가 현실적
- 트라이얼 없는 순수 프리미엄 전환율(다운로드→구매)은 업계 평균 약 2%

**종합 목표치**: 설치→체험 약 10%, 체험→유료 약 20~25% → **다운로드 대비 최종 유료 전환율 약 2~2.5%**

### 2-7. SOM (Year 1 목표)

SAM(25만~32만 커플)의 1% 침투 가정 시:

| 단계 | 전환율 | 결과 |
|---|---|---|
| 앱 인지·다운로드 | SAM의 1% | 2,500~3,200 커플 (개인 5,000~6,400명) |
| 다운로드→체험 시작 | ~10.9% | 545~700명 |
| 체험→유료 전환 | ~25% | **약 136~175명 (유료 결제 68~87커플)** |

### 2-8. ONDOLOG가 겹쳐있는 시장

네 개 시장의 교집합에 위치한다.

1. **커플 앱 시장** — 직접 경쟁: 비트윈, 썸원. 검증된 국내 수요 존재
2. **자기이해/개인화 콘텐츠 시장** — MBTI·사주·타로 인접, 커플 전용 강자 부재
3. **AI 생성 콘텐츠(AIGC) 시장** — 기술 인프라 순풍
4. **개인화 디지털 구독 콘텐츠 시장** — 전환율 벤치마크의 기준점

명확한 단일 카테고리가 없다는 점이 리스크이자 기회다 — 마케팅 포지셔닝을 스스로 정의해야 한다.

## Part 3. 솔루션 (Solution)

### 3-1. 핵심 컨셉

> **"우리의 연애를, 우리만의 잡지로."**
> 커플이 남긴 기록을 AI가 읽고 정기적으로 발행되는 잡지 콘텐츠로 되돌려주는 서비스

### 3-2. 세 가지 핵심 기능

1. **아카이브 (Archive)** — 커플 데이터(대화, 사진, 데이트 기록, 성격검사 결과)를 입력·축적하는 기반 레이어
2. **매거진 발행 (Publish)** — AI가 축적된 데이터를 읽고 정기적으로 포맷화된 잡지를 자동 생성·발행. 감정 노이즈를 걸러내고 의미 있는 순간 위주로 재구성
3. **커플 SNS (Connect)** — 매거진을 매개로 커플이 함께 반응·상호작용하는 공간

### 3-3. 아홉 가지 세부 항목

| # | 항목 | 내용 | MVP |
|---|---|---|---|
| 1 | 데이터 입력 방식 | 수동 업로드 + 사진 앱 자동 연동 | ✅ 자동 연동 포함 |
| 2 | AI 편집 로직 | 감정 분석 기반 노이즈 필터링 + 하이라이트 선별 | ✅ 단순 선별부터 |

### 3-7. 전 코너 공통 원칙 (절대 규칙)

> **원문 우선, AI는 판정하지 않는다. 없는 걸 지어내지 않는다.**

AI는 **관찰하고 짚어줄 수 있다.** 감정의 결을 읽고 긍정적인 목소리를 내는 것은
이 서비스의 가치에 포함된다. 그걸 막으면 코너가 데이터 나열이 된다.

다만 **주체에 따라 평이 갈리는 지점에는 개입하지 않는다.**

| 허용 | 금지 |
|---|---|
| 유저 원본을 지면의 주인공으로 배치 | 원본을 대체하거나 각색 |
| 감정·분위기를 짚어주기 | **잘잘못 판정** |
| 긍정적 방향의 목소리 | **한쪽 편들기** |
| 변화를 관찰해 서술 | **관계에 대한 진단·훈수** |
| 두 사람 모두에게 해당하는 서술 | **특정인의 행동을 문제 삼기** |
| 데이터가 없으면 스킵하거나 분량 축소 | 데이터가 없는데 억지로 만들어내기 |

**판단 기준**

> 이 문장을 두 사람이 **각자** 읽었을 때, 한쪽이라도 불편해질 여지가 있는가.
> 있으면 쓰지 않는다.

예시로 보면 명확하다.

| 문장 | 판정 |
|---|---|
| "이날은 서로 조심스러웠던 것 같습니다" | ✅ 두 사람 모두에 해당 |
| "오늘 두 분 정말 다정하셨네요" | ✅ 긍정 방향, 편이 갈리지 않음 |
| "8월에는 우산 이야기가 네 번 나왔습니다" | ✅ 사실 서술 |
| "이날은 세준이 먼저 사과했어야 했습니다" | ❌ 잘잘못 판정 |
| "서영의 서운함이 이해되는 상황입니다" | ❌ 한쪽 편들기 |
| "두 분은 대화가 부족합니다" | ❌ 관계 진단 |
| "답장에 소홀해졌습니다" | ❌ 개인의 태도를 문제 삼음 |

**AI는 편집자이지 심판이 아니다.**

## Part 4. 성장 전략 (Scale-up)

### 4-1. 수익 모델 우선순위

1. **1순위 — 구독 전환율 검증**: 발행물 체험 후 유료 전환이 핵심 지표
2. **2순위 — 리텐션 기반 확장**: 참여형 코너, 티어 세분화는 리텐션 데이터 확보 후
3. **3순위 (Year 2) — 실물 발행물**: 구독 충성도 높은 유저 대상 프리미엄 옵션

### 4-2. 티어 구조

| 티어 | 가격(안) | 포함 내용 |
|---|---|---|
| Free | 0원 | 데이터 입력·아카이브, 잡지 발행 첫 1회 무료 체험, **최근 3개월 기록만 열람** |
| 유료 구독 | 월 9,900원 (커플 단위, 제안값) | 정기 발행, 전체 코너, 공유 카드 무제한, **전 기간 기록 열람** |

### 4-3. 전환 시나리오 (예시 코호트 1,000명)

```
가입 1,000명
  ↓ 온보딩 완료 (약 70%, 추정)
700명
  ↓ 첫 데이터 입력 시작 (약 60%, 추정)
420명
  ↓ 첫 호 무료 발행 도달 (약 50%, 추정)
210명
  ↓ 체험 → 유료 전환 (25%, 업계 벤치마크)
약 52명 (26커플) 유료 전환
```

> 온보딩·입력·발행도달 비율은 업계 관행값 추정치. **MVP 출시 후 최우선 검증 지표.**

### 6-2. Expo Go 사용 불가 확정 사유

피드 탭의 **얼굴 인식 기반 데이트 사진 선별** 기능이 네이티브 모듈(iOS Vision / Android ML Kit)을 요구한다. 따라서 프로젝트 **초기부터 EAS Dev Build로 개발**한다.

| 상황 | 판단 |
|---|---|
| 순수 JS 로직, 기본 Expo 모듈만 | Expo Go로도 가능하나, 어차피 Dev Build가 필요하므로 통일 |
| 얼굴 인식, 세분화 권한, 딥링크 | **Dev Build 필수** |

### 6-3. 선행 프로젝트에서 얻은 교훈 (반복 금지 목록)

**① 버전 고정**

- **문제**: `create-expo-app`에 SDK별 dist-tag가 없어 최신으로 스캐폴딩 후 `expo` 패키지만 수동 재조정 필요. `npx expo install --fix`가 내부 `autoAddConfigPlugins.js`에서 반복 크래시.
- **예방**: 목표 SDK 버전을 CLAUDE.md에 명시. 크래시 시 우회 절차(로그에서 권장 버전 추출 → `npm install --legacy-peer-deps`)를 표준 절차화.

**② 의존성 충돌**

- **문제**: `react-native-reanimated` 4.x 비호환으로 강제 다운그레이드 필요. `react`가 `expo install` 과정에서 조용히 상위 버전으로 bump.
- **예방**: 착수 시 호환 매트릭스 확인. `expo install` 실행 후 `package.json` diff를 항상 확인.

**③ 네트워크/터널링**

- **문제**: `--tunnel`이 `ERR_NGROK_3004`로 실패.
- **예방**: 동일 네트워크에서는 `--lan` 사용. 외부 네트워크 필요 시 ngrok 토큰 사전 확보.

**④ 파일명 인코딩**

- **문제**: 한글 파일명 ZIP이 iOS에서 확장자 미인식.
- **예방**: **모든 산출물 파일명은 영문+숫자(ASCII)만 사용.**

## Part 7. PRD — 개요 및 기능 요구사항

### 7-1. 개발 관점 한 줄 요약

> 커플이 사진·메모·대화를 입력하면, AI가 코너 단위로 조합해 정기적으로 커플 매거진을 발행하는 앱

### 7-2. 핵심 기술 과제

입력된 원본 데이터(사진, 텍스트, 성격검사 결과)를 **AI가 코너 단위로 편집·조합해 완결된 콘텐츠(잡지)로 변환**하는 파이프라인이 제품의 본질이다. 나머지(아카이브, SNS 기능)는 이를 지탱하는 인프라다.

### 7-3. 개발 우선순위 근거

유저 저니맵상 **"첫 호 발행(체험)" 단계가 전체 퍼널의 병목**이다. 따라서 리소스 배분 원칙:

1. 최우선 — 코너별 AI 생성 파이프라인의 완성도
2. 차순위 — 데이터 입력 UX (입력 마찰이 적을수록 발행물 재료가 쌓임)
3. 그 다음 — 결제/구독 전환 플로우

### 7-4. 유저 저니맵

| 단계 | 유저 행동 | 감정 | ONDOLOG의 역할 |
|---|---|---|---|
| 1. 인지 | 인스타 릴스/카드뉴스에서 결과 카드를 봄 | 호기심 | 공유 가능한 요약 카드로 바이럴 유도 |
| 2. 설치·가입 | 앱 다운로드, 가입 후 파트너 초대 | 기대 + 진입장벽 | 파트너 미연결 상태에서도 최소 가치 제공 |
| 3. 온보딩 | 성격검사 응답, 초기 정보 입력 | 재미 | 짧고 가벼운 온보딩으로 이탈 방지 |

| 5. **첫 호 발행** | 무료 체험판 잡지 수령 | **핵심 모멘트** | 퍼널 전체의 성패가 걸린 지점 |
| 6. 반응·공유 | 커플이 함께 반응, SNS 공유 | 만족 | 공유 요약 카드 자동 생성 |

### 8-2. 초안 대비 핵심 변경 7가지

| # | 변경 | 사유 |
|---|---|---|
| 1 | `users` → `profiles` (auth.users 확장) | Supabase Auth 표준 |
| 2 | `personality_*` 2분할 (assessments / profiles) | 재검사 1회 제한 + 원본 보존 + 오버라이드 무제한을 한 테이블로 담으면 "현재값"이 모호해짐 |
| 3 | `dates` / `date_stops` 신설 | "하루 = 한 기사" 구조. 클러스터링 결과를 영속화해 재계산 비용 제거, 유저 보정값의 귀속 지점 명확화 |
| 4 | `stat_snapshots` / `match_reports` / `dna_scores` 신설 | 연애리그 월간판의 "왜 스탯이 변했나"는 시계열 없이는 생성 불가 |
| 5 | `messages` / `stories` 분리 | 만료·연동 분기 로직이 서로 다름 |
| 6 | **`corners.content` = 스냅샷** (참조 아님) | 8-3 참조 |
| 7 | 3개월 초과분 삭제 → `access_locked` | 지우지 않고 잠근다 |

### 8-3. 가장 중요한 설계 판단 — 매거진은 동결된 산출물

"탈퇴자 파생 데이터는 삭제하되 발행된 매거진은 보존"이라는 정책은, 코너가 원본을 **참조만 하면 논리적으로 성립하지 않는다.** 원본이 사라지면 코너가 깨진다.

따라서 `corners.content`(jsonb)에 렌더링에 필요한 **모든 값을 복사해서** 담는다.

| 대상 | 처리 |
|---|---|
| 텍스트 (메시지 본문, 유저 메모) | id가 아니라 **문자열 자체**를 저장 |
| 미디어 | 발행 시점에 **`magazine` 버킷으로 복제**하고 경로 치환 |
| 작성자 이름 | 복사 저장 (탈퇴 후 profiles 조회 불가) |
| `source_*_ids` | 감사·표시용 참고 배열. **FK 아님**, dangling 허용 |

> 미디어 복제를 건너뛰면 원본 삭제 시 발행물에 빈 이미지가 뜬다. 스냅샷 원칙은 텍스트뿐 아니라 **미디어에도 적용**된다.

### 8-4. 얼굴 데이터 — 스키마 수준의 방어

| 대상 | 처리 |
|---|---|
| 대표 사진 원본 (개인 1장 / 커플 1장) | Storage 저장 **허용** — 일반 사진과 동일. 파트너 기기도 인식해야 하므로 동기화 필요 |
| 얼굴 임베딩 / 특징점 벡터 | **DB·Storage 어디에도 저장 금지.** 기기 보안 저장소 전용 |

임베딩을 담을 컬럼을 **의도적으로 만들지 않았다.** `ONDOLOG_SCHEMA.md` §14에 임베딩 관련 컬럼명이 존재하면 실패하는 검증 쿼리를 두어, 나중에 편의상 추가되는 것을 막는다.

### 8-5. RLS 원칙

- 19개 테이블 **전부** RLS 활성화
- `is_couple_member(uuid)`를 `SECURITY DEFINER STABLE`로 정의해 재귀 평가 회피
- 자식 테이블에 `couple_id` 비정규화 → 정책이 인덱스 한 번으로 종료
- **인쇄용 PDF는 RLS로 못 막는다** (RLS는 행 단위, 컬럼 은닉 불가)
  → `issues` 테이블을 클라이언트에서 revoke하고 `pdf_print_path`를 제외한 `issues_public` 뷰만 노출

### 8-6. 채점 룩업 vs 표시 라벨

| 대상 | 위치 | 이유 |
|---|---|---|
| 호나이×하모닉 9칸, 애착 2×2, 빅5 가중치 | `src/constants/` (코드) | **결정론 계약** — DB가 바뀌면 과거 결과가 재현되지 않는다 |

#### 화면 6 약관 동의 명세 — 배경

`profiles` 테이블은 `terms_agreed_at`, `privacy_agreed_at`을 NOT NULL로 요구한다. 그런데 화면 명세에 동의 절차가 없어, 구현 시 **약관을 보여주지 않고 동의 시각만 기록**하는 상태가 된다.

이는 법적으로 무효다. 개인정보보호법상 동의는 정보주체가 **내용을 확인할 수 있는 상태에서 명시적으로 표시**해야 성립한다. 기록만 남기는 것은 동의가 아니다.

ONDOLOG는 채팅 원문·사진·얼굴 정보를 다루므로 이 부분이 특히 중요하다.

#### 6-1. 화면 구성

| 순서 | 요소 |
|---|---|
| 1 | 소셜 로그인 3종 (카카오 / 구글 / 애플) |
| 2 | **동의 항목 체크리스트** |
| 3 | "동의하고 시작하기" 버튼 (필수 항목 전체 체크 시에만 활성화) |

**순서 원칙**: 소셜 로그인을 먼저 누르는 게 아니라, **동의를 먼저 받고 로그인**한다. 인증 후 동의를 받으면 이미 계정이 생성된 뒤라 "동의하지 않음" 처리가 복잡해진다.

#### 6-2. 동의 항목

| # | 항목 | 필수 | DB 컬럼 |
|---|---|---|---|
| 1 | 만 14세 이상입니다 | 필수 | (검증만, 컬럼 없음) |
| 2 | 이용약관 동의 | 필수 | `terms_agreed_at` |
| 3 | 개인정보 처리방침 동의 | 필수 | `privacy_agreed_at` |
| 4 | **AI 콘텐츠 생성을 위한 데이터 활용 동의** | 필수 | `ai_usage_agreed_at` |
| 5 | 마케팅 정보 수신 동의 | 선택 | (별도 컬럼 신설 필요) |

**"전체 동의" 체크박스**를 상단에 두되, 개별 항목도 각각 체크 가능해야 한다.

#### 6-3. 각 항목의 UI 요구사항

**공통**: 동의 대상 문서가 있는 항목(②③④⑤)에는 전문을 볼 수 있는 **[보기]** 링크를 반드시 둔다. 링크 없이 체크박스만 두면 동의로 인정되지 않는다. **①은 자동 검증 항목(볼 문서 자체가 없음)이라 해당 없음.**

**① 만 14세 이상**
- 화면 2에서 수집한 `birth_date`로 **자동 검증**한다
- 만 14세 미만이면 체크 불가 + 안내 문구 노출 후 가입 차단
- 안내: *"만 14세 미만은 서비스를 이용할 수 없습니다"*

> ⚠️ **정책 결정 필요**: 만 14세는 개인정보보호법상 법정대리인 동의 없이 본인 동의가 가능한 최저 연령이다. ONDOLOG는 커플 대상 서비스이고 사진·채팅·얼굴 정보를 다루므로, 운영 정책상 더 높은 연령(예: 만 19세)을 하한으로 둘지 검토가 필요하다. 이 결정 전까지는 만 14세를 적용한다.

**② 이용약관**
- 전문 노출 (모달 또는 별도 화면)
- 발행 매거진의 공동 저작물 조항 포함 (Part 16 법무 과제)

**③ 개인정보 처리방침**
- 수집 항목, 이용 목적, 보관 기간, 제3자 제공 여부 명시
- **무료 티어 3개월 보관 정책을 여기서 고지**한다 (출시 시점 고지가 전제였음)

**④ AI 데이터 활용 동의 (ONDOLOG 고유)**
- **별도 필수 항목으로 분리한다.** 이용약관에 묻어가면 안 된다
- 고지 내용에 반드시 포함할 것:
  - 채팅 대화, 사진, 메모가 매거진 생성에 사용된다
  - 이 과정에서 외부 LLM API로 데이터가 전송된다
  - 사용되는 프로바이더와 그 데이터 보존·학습 정책
- 톤은 "AI 매거진 메이커" 캐릭터로 부드럽게 하되, **법적 고지문은 그대로 노출**한다
  → 캐릭터화는 정서적 민감도를 낮추는 장치이지 법적 요건을 대체하지 않는다

**⑤ 마케팅 수신 (선택)**
- 미체크 상태가 기본값
- 선택 항목임을 명시

#### 6-4. 이 화면에 포함되지 않는 것

| 항목 | 이유 | 시점 |
|---|---|---|
| **생체정보(얼굴) 동의** | 민감정보라 **별도 화면·별도 시점**에 받아야 함 | Phase 6, 사진 앱 연동 시 |
| 위치정보 동의 | 사진 EXIF 사용 시점에 | Phase 6 |
| 푸시 알림 권한 | OS 권한이라 온보딩 후 | Phase 4 이후 |

생체정보 동의를 가입 시점에 함께 받으면, 유저는 무엇에 동의했는지 인지하지 못한다. 실제로 그 기능을 켜는 시점에 받아야 유효한 동의가 된다.

#### 6-5. 데이터 처리

```
동의 체크 완료
  → "동의하고 시작하기" 탭
  → 소셜 로그인 인증
  → 인증 성공 시 profiles 레코드 생성
     terms_agreed_at   = now()
     privacy_agreed_at = now()
     ai_usage_agreed_at = now()
  → 화면 2~5 세션 데이터를 계정에 귀속
  → 화면 7(상세 결과)로 이동
```

**인증 실패 시**: 동의 상태를 세션에 유지하고 재시도 가능하게 한다. 다시 체크하게 만들지 않는다.

#### 6-6. 완료 기준

- [ ] 필수 항목 4개를 모두 체크해야 버튼이 활성화된다
- [ ] 문서가 있는 항목(②③④⑤)에 전문 [보기] 링크가 존재한다 (①은 해당 없음)
- [ ] `birth_date` 기준 만 14세 미만은 가입이 차단된다
- [ ] AI 활용 동의가 이용약관과 **분리된 별도 항목**이다
- [ ] 생체정보 동의 항목이 이 화면에 **없다**
- [ ] 인증 실패 후 재시도 시 동의 상태가 유지된다
- [ ] 동의 없이 `profiles` 레코드가 생성되지 않는다

#### 연애 온도

> **계산 규격은 Part 10-7이 원본이다.** 이 절에는 계산식·계수를 적지 않는다.
> 여기에 남는 것은 표시 규격뿐이다. 숫자가 두 곳에 있으면 반드시 어긋난다.

| 항목 | 내용 |
|---|---|
| 계산 규격 | **Part 10-7 참조** (기저 + 변동 구조) |
| **갱신 주기** | **일 단위 배치** (Supabase Edge Function, 자정 실행) |
| 앱 동작 | 저장된 값을 읽기만 함 — 실시간 계산 금지 (비용·응답속도) |
| 미연결 시 | 36.5도 고정 |

**표시 규격**

| 항목 | 규격 |
|---|---|
| 표기 | 소수점 첫째 자리까지 (`numeric(4,1)`), 단위 `°` |
| 범위 | 0~100 (클램프는 Part 10-7) |
| 보조 문구 | 아래 고정 문구. **연결 후에만 노출** |

**온도 히어로 보조 문구 (확정, 연결 후 한정)**

> 온도가 잘 맞는 유형일수록 시작 온도가 조금 높습니다.
> 나머지는 두 사람이 만들어갑니다.

| 항목 | 내용 |
|---|---|
| 노출 조건 | 커플 연결 완료 + 양측 성격 프로파일 존재 |
| 미연결 시 | 노출하지 않는다 (36.5° 고정 상태에서는 사실이 아니다) |
| 대응 문구 | 연결 전 안내는 화면 7 궁합 섹션 하단 (Part 9-1) |

**설계 의도.** Part 10-7의 기저 + 변동 구조에서 유형 궁합이 실제로 기저
온도를 정한다(36.5 / 39 / 42). 두 번째 문장이 이 사실을 감추지 않으면서도
운명론적 읽기를 막는다 — 기저 차이는 5.5인 반면 활동 폭은 55이므로
**2주만 꾸준해도 기저 차이가 뒤집힌다**는 실제 배분과 일치하는 서술이다.
Part 10-6-0("이 표는 운명이 아니다")과 같은 방향이다.

> ⚠️ **"기본 체온"이라는 표현을 쓰지 않는다.** 이 문서는 36.5를 "아직 아무
> 데이터도 없는 평온한 기본 체온"으로 정의하고 있다. 기저가 39·42인 커플에게
> "기본 체온이 높다"고 하면 그 정의와 충돌한다. **"시작 온도"**로 통일한다.

**표시 상태**

| 상태 | 표시 |
|---|---|
| 미연결 | 36.5° (고정) |
| 연결 + 성격 프로파일 미완 | 36.5° (기저 산출 불가) |
| 연결 + 활동 0일 | "아직 온도를 잴 기록이 없어요" |
| 연결 + 활동 1일 이상 | 실제 온도 |

> ⚠️ 이전 규격에서는 "배치값 없음"이 빈 상태의 조건이었다. Part 10-7이
> 이동창 분모를 14로 고정하면서 활동 0일에도 기저 온도가 산출되므로,
> 빈 상태는 **활동 0일 한정**으로 좁아졌다.

> "다음 발행까지 남은 기간"은 발행 주기 config가 확정된 Phase 7 이후 구현한다.

#### AI 데이터 활용 고지 방향

**캐릭터화하지 않는다.** 서술자는 인격체가 아니라 목소리다.

캐릭터를 만들면 관계가 생기고, 관계가 생기면 말을 걸게 되고, 말을 걸면
판정하게 된다 — Part 3-7과 충돌한다. 발행물 실물에도 화자가 등장하지 않으며,
목차 문장의 주어는 인격체가 아니라 "온도록"이라는 서비스명이다.

**서술 규격** (기존 원칙으로 충분하다)

| 항목 | 규격 |
|---|---|
| 인칭 | 3인칭. "두 사람은", "세준이 남긴 메모" |
| 주어 | 필요할 때만 "온도록". 1인칭 금지 |
| 태도 | 관찰·서술·긍정적 목소리 가능. 판정 금지 (Part 3-7) |
| 데이터 없을 때 | 스킵하거나 분량 축소 |

**민감도는 캐릭터가 아니라 정직한 고지로 다룬다.**
- 온보딩 화면 6의 AI 데이터 활용 동의 (별도 필수 항목)
- 발행물 고지 문구 — 예: *"수록된 사진과 문장은 두 사람이 남긴 기록이며,
  편집 외의 각색은 하지 않았습니다."*

### 9-4. 피드(히스토리) 탭

#### 화면 구성

| 영역 | 요소 |
|---|---|
| 상단 | 뷰 전환 토글 — **피드형 / 지도형** |
| 본문(피드형) | 인스타그램 스타일 그리드/세로 스크롤 |
| 본문(지도형) | 카카오맵 위에 데이트 핀 + 코스 연결선 |
| 하단 | 업로드 플로팅 버튼 |
| 게이팅 | 부분 — 혼자서도 업로드 가능, 통합 뷰는 커플 전용 |

#### 사진 자동 연동 + AI 데이트 인식 (핵심 기능)

**동작 흐름**

```
사진 앱 권한 허용
  → 라이브러리 스캔
  → ① 얼굴 인식으로 "우리 커플이 찍힌 사진"만 선별
  → ② EXIF(촬영시각·GPS)로 시공간 클러스터링 → 한 건의 "데이트"로 묶음
  → ③ AI가 사진 간 연관성을 해석해 서사 생성
  → ④ 피드/지도에 자동 게시
  → ⑤ 유저는 위치 수정, 감정 기록, 사진 위 드로잉으로 보정
```

**③ 서사 생성 예시**

> 2026.08.19 · 연남동
> 사진1 — 홍대 영화관에서 스파이더맨 관람
> 사진2 — 영화 후 OO식당에서 식사
> 사진3 — 연남동 카페 방문

**핵심 원칙**: 유저가 데이터를 직접 입력하지 않는다. AI가 자동 인식하고, 유저는 **보정만** 한다.

**연인 인식용 대표사진**

| 항목 | 내용 |
|---|---|
| 등록 | **개인 1장 + 커플 1장**, 프로필처럼 관리 |
| 용도 | 수천 장의 라이브러리에서 "우리 데이트"만 골라내는 기준 얼굴 |
| 수정 | 설정 탭에서 언제든 교체 |

**⚠️ 얼굴 정보 처리 — 온디바이스 전용 (절대 규칙)**

한국 개인정보보호법상 얼굴 특징점은 **생체인식정보 = 민감정보**로, 별도의 명시적 동의가 필요하다.

| 항목 | 규칙 |
|---|---|
| 특징점 추출·매칭 | **전부 기기 내에서 수행** |
| 서버 전송 | 얼굴 특징 벡터는 **어떤 경우에도 전송하지 않음** |
| 서버 저장 | "이 사진은 데이트다"라는 판정 결과와 유저가 선택한 사진만 |
| 동의 | 일반 약관과 **분리된 별도 동의 화면** |
| 철회 | 설정 탭에서 언제든, 철회 시 로컬 데이터 즉시 삭제 |

> "당신의 얼굴은 폰 밖으로 나가지 않습니다"는 강력한 마케팅 메시지가 된다. 비트윈 데이터 소실 사고 이후 프라이버시 신뢰는 핵심 차별점이다.

**성능 전략**

- 최초 1회 전체 스캔은 백그라운드·충전 중 우선 실행
- 이후 신규 사진만 증분 처리
- 스캔 진행률을 유저에게 가시화 (블랙박스 금지)

#### 입력 방식

| 방식 | 내용 |
|---|---|
| 사진 | 자동 인식 + 수동 업로드. EXIF 시각·GPS 추출, 유저가 장소명 수정 가능 |
| 글쓰기 | 자유 텍스트 + 드로잉 (iOS 메모장 수준의 자유도) |
| 해시태그 | 선택적. "해시태그를 달면 AI가 더 잘 구분해요" 안내 |
| 감정 기록 | 사진 위에 느낌을 쓰고 그릴 수 있음 |

#### 지도

| 항목 | 내용 |
|---|---|
| 1순위 | **카카오맵 API** (국내 장소 정확도) |
| 대안 | 난항 시 구글맵 API 전환 — 추상화 레이어 필수 |

#### 미연결 유저

혼자서도 기록 가능. 개인 대표사진만으로 자동 인식 동작. 커플 연결 시 양측 기록이 하나의 타임라인으로 병합.


#### 생체정보(얼굴 인식) 별도 동의 — 배경

가입 시점에 얼굴 인식 동의를 함께 받으면 유저는 무엇에 동의했는지 인지하지 못한다. **실제로 그 기능을 켜는 시점**에, 무엇을 위해 얼굴을 인식하는지 눈앞에서 설명하고 동의받아야 유효하다.

개인정보보호법상 얼굴 특징점은 생체인식정보(민감정보)로, 일반 약관과 **분리된 명시적 동의**가 필요하다. ONDOLOG는 이 동의를 **얼굴 특징 추출이 실제로 실행되기 직전**에 받는다.

---

#### 화면 순서 — 피드 탭 최초 진입 시

```
피드 탭 최초 진입
  → (사진 앱 미연동) "사진 자동으로 정리해드릴까요?" 안내 카드
  → [연동하기] 탭
  → 화면 A: 생체정보 동의
  → 동의 시 → 화면 B: OS 사진 라이브러리 권한 요청 (표준 다이얼로그)
  → 권한 허용 시 → 화면 C: 대표사진 등록
  → 등록 완료 → 백그라운드 스캔 시작
```

**동의를 얼굴 인식 실행 직전에 배치**하는 게 핵심이다. 사진 라이브러리 권한(OS 표준)보다도 **먼저** 온다 — 라이브러리에 접근하는 이유 자체가 얼굴을 찾기 위해서이므로, 그 목적을 먼저 설명해야 한다.

#### 화면 A. 생체정보 동의

##### 구성

| 순서 | 요소 |
|---|---|
| 1 | 헤드라인 — 무엇을 위한 동의인지 |
| 2 | 동작 설명 (3단계, 그림 없이 텍스트로) |
| 3 | **온디바이스 처리 고지** (핵심 조항) |
| 4 | 전문 [보기] 링크 |
| 5 | 동의 체크박스 (단일 필수 항목) |
| 6 | [동의하고 계속] / [나중에] |

##### 헤드라인 (예시 — 최종 문구는 콘텐츠 확정 시 대체)

> 우리 둘이 함께 있는 사진만 찾아드릴게요

##### 동작 설명 — 담백하게, 과장 없이

```
1. 두 사람의 얼굴을 기준 사진으로 등록합니다
2. 사진 라이브러리에서 두 사람이 함께 있는 사진만 찾습니다
3. 찾은 사진은 자동으로 피드에 정리됩니다
```

##### 온디바이스 처리 고지 — 반드시 포함할 문구 요지

법적 효력이 있는 조항이므로 **자리표시자로 두되 반드시 아래 내용을 담을 것**:

- 얼굴 특징 정보는 **이 기기 안에서만** 처리되며 서버로 전송되지 않는다
- 대표사진 원본(사진 파일 자체)은 서버에 저장될 수 있으나, 그로부터 추출한 얼굴 특징 데이터는 저장되지 않는다
- 동의는 언제든 설정 탭에서 철회할 수 있으며, 철회 시 기기에 저장된 얼굴 특징 데이터가 즉시 삭제된다
- 이 동의를 거부해도 앱의 다른 기능(수동 업로드 포함)은 그대로 이용할 수 있다
> ⚠️ 정확한 법률 문구는 `legalDocuments.ts`의 다른 자리표시자와 동일한 원칙을 따른다 — **지어내지 않는다.** 실제 조문은 법무 검토 후 확정.

##### 동의 체크박스

단일 항목, 단일 목적. Part 9-1 화면 6처럼 여러 항목을 묶지 않는다 — 이 동의는 **얼굴 인식이라는 하나의 목적**에만 쓰인다.

```
[ ] 위 내용에 동의하며, 얼굴 인식 기반 사진 자동 정리 기능을 사용합니다
```

- [ ] 동의 없이는 화면 B(권한 요청)로 진행되지 않는다
- [ ] [나중에] 선택 시 피드 탭으로 복귀, 수동 업로드는 계속 가능
- [ ] 온디바이스 처리 고지가 반드시 노출된다 (스킵 불가)
- [ ] 전문 [보기] 링크가 동작한다

기존 스키마의 `biometric_consent_at`, `biometric_consent_revoked_at`을 그대로 쓴다.

```sql
-- 동의 시
update profiles set biometric_consent_at = now() where id = :user_id;

-- 철회 시 (설정 탭)
update profiles
  set biometric_consent_revoked_at = now(),
      reference_photo_path = null
  where id = :user_id;
```

**철회 시 반드시 함께 일어나야 하는 일**:

1. `biometric_consent_revoked_at` 기록
2. `reference_photo_path` 삭제 (대표사진 원본)
3. **기기 로컬의 얼굴 특징 데이터 삭제** — 이건 서버 컬럼이 아니라 클라이언트 로직. `rule-auditor`가 검증할 수 없는 유일한 항목이므로 QA 체크리스트에 수동으로 남겨야 한다
4. 이후 자동 인식 중단, 수동 업로드만 가능한 상태로 전환

#### 얼굴 인식 아키텍처 — 탐지와 인식은 다른 문제다

**얼굴 탐지**(사진에 얼굴이 있는가, 몇 개인가)와 **얼굴 인식**(그 얼굴이 누구인가)은 다른 기술이다. ONDOLOG는 "사진에 얼굴이 있다"가 아니라 **"이 사진이 우리 커플이다"**를 판별해야 하므로 인식이 필요하다.

또한 이건 실시간 카메라 문제가 아니라 **이미 촬영된 사진 라이브러리를 배치로 스캔**하는 문제다. `react-native-vision-camera` 계열(프레임 프로세서)은 라이브 카메라 프레임 처리에 최적화되어 있어 이 용도에 맞지 않는다.

#### 3단계 파이프라인

```
1단계 — 얼굴 탐지
   사진 속 얼굴의 위치를 찾는다 (있는지, 몇 개인지, 어디에)

2단계 — 임베딩 추출
   탐지된 얼굴을 고정 길이 숫자 벡터로 변환한다

3단계 — 매칭
   벡터 간 유사도(코사인 거리)를 계산해 대표사진과 비교,
   임계값 이내면 "우리 커플"로 판정
```

**설계상 중요한 지점**: 1·2단계만 네이티브 SDK 의존이고, **3단계(매칭)는 순수 계산**이다. 벡터 두 개를 받아 유사도를 반환하는 함수는 `engine-dev`가 짜는 채점 로직과 성격이 같다 — 입력이 같으면 출력이 같은 결정론적 순수 함수로 만들 수 있다.

```
src/engine/faceMatch.ts       ← 순수 함수. 벡터 비교만. 라이브러리 의존 없음
src/services/faceRecognition/ ← 네이티브 SDK 래퍼. 1·2단계
```

이렇게 나누면 매칭 로직에 결정론 테스트(§Part 17-3과 같은 패턴)를 붙일 수 있고, 나중에 라이브러리를 교체해도 매칭 함수는 그대로 유지된다.

##### 매칭 판정 정책 (확정)

**오탐 회피를 우선한다.** 임계값은 "우리 커플이 아닌 얼굴이 발행물에 실릴
확률"을 먼저 낮추는 방향으로 정하고, 그 대가로 발생하는 미탐(우리 사진이
잡히지 않음)은 허용한다. **판정이 애매한 구간은 매칭하지 않는 쪽으로 처리한다.**

| 근거 | 내용 |
|---|---|
| 오탐 | 제3자의 동의 없는 얼굴이 발행물에 실리는 사고. **인쇄본은 회수할 수 없다** |
| 미탐 | Phase 6-7단계 EXIF 클러스터링으로 부분 보완. 매거진 제작 탭(Phase 10) 도입 후 사람이 되살릴 수 있다 |

**이중 임계값**(애매 구간을 유저에게 확인)은 이번 범위에 넣지 않는다.
유사도 분포를 관측한 뒤 Phase 10과 묶어 재검토한다.

**임계값 자체는 미확정이다.** SDK 반환값이 유사도인지 거리인지, 정규화
범위가 무엇인지, 실제 커플 사진에서 어느 대역에 분포하는지가 전부
재빌드 후 실기기에서만 관측된다. 지금 숫자를 정하면 근거가 없다.
코드에서는 `UNRESOLVED('faceMatch.threshold')`로 둔다.

> ⚠️ **측정은 온디바이스에서만 한다.** 유사도 분포를 수집한다며 특징 벡터나
> 유사도 로그를 서버로 보내면 절대 규칙 1 위반이다. 화면에서 읽고 손으로
> 기록하는 형태여야 한다. 실기기 캘리브레이션이므로 위임 대상이 아니라
> 메인 세션 작업이다.

### 9-5. 매거진 탭

> 매거진 탭은 **결과물을 보는 곳이자, 만들어지는 과정에 참여하는 곳**이다.
> 발행된 호는 서재에, 제작 중인 호는 진행률과 입력 창구로 보여준다.

#### 화면 구성

```
매 거 진
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

┌────────┐
│░░░░░░░░│   9월호  제작 중        24%
│░░░░░░░░│   ━━━━━━━━━━━━━━━━━     ← 실루엣 + 진행률
│░░░░░░░░│
└────────┘
─────────────────────────────
 Vol.02   Vol.01                    ← 서재 (발행 완료분)
```

#### 다음 호 실루엣

발행 대기 중인 호를 **표지 실루엣**으로 서재 맨 앞에 놓는다. 발행물이 쌓일수록 "다음 호가 만들어지는 중"이 자연스럽게 시야에 들어온다.

| 상황 | 표시 |
|---|---|
| 제작 중 | 실루엣 + 진행률 |
| 발행 직후 | 실루엣 + `0%` + "9월호가 시작되었습니다" |
| 첫 호 (연결 직후) | 실루엣 + `0%` + "첫 호를 만들기 시작했어요" |
| 미연결 | 실루엣만, 진행률 없음. 초대 CTA |

**실루엣 규격**: 표지 비율(1:1.414)을 그대로 쓰되 이미지 자리를 `paper-alt` 단색으로 채운다. 그림자·플레이스홀더 아이콘 없이 **빈 지면**으로 둔다.

#### 제작 진행률 화면

실루엣을 탭하면 이 화면으로 들어간다. **매거진 제작에 필요한 입력 항목의 상태**를 보여주고, 대기 중인 항목은 바로 입력 화면으로 연결된다.

```
8 월 호  제 작 중                      68%
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

데이트 아카이브                    준비됨
사진 34장 · 메모 2

우리의 연애 DNA                    준비됨

다정한 말들                        준비됨
대화 412건 분석

우리 사이 인터뷰                   대기 중  →
3문항 중 1문항 답변

오프라인 셋로그                    대기 중  →
이번 주 2일 기록

이달의 우리                        준비됨
```

**설계 의도 두 가지**

첫째, **참여 요청이 알림이 아니라 화면에 상주한다.** 알림은 놓치면 끝이지만, 매거진 탭을 열 때마다 대기 중 항목이 보인다. 리텐션 장치가 자연스럽게 생긴다.

둘째, **미참여의 결과가 눈에 보인다.** "안 하면 이 코너가 안 실린다"는 게 퍼센트로 드러나니, 재촉하지 않고도 동기가 생긴다. Part 9-1의 "잠긴 문을 보여주는 게 낫다"는 원칙과 같은 계열이다.

| 항목 | 규격 |
|---|---|
| 진행률 계산 | 코너별 준비 상태의 가중 평균 |
| 구분 | **자동 수집 코너**(데이터만 쌓이면 됨)와 **참여 필요 코너**를 구분한다. 유저가 움직일 수 있는 건 후자뿐 |
| "대기 중" 탭 | 해당 코너의 입력 화면으로 이동 (인터뷰 → 답변, 셋로그 → 사진 업로드) |
| 정체 상태 | 진행률이 멈춰 있어도 대기 항목이 명시되어 있으면 "고장났나" 오해가 없다 |

> **매거진 제작 탭은 참여형 코너의 유일한 입력 창구다.** 코너마다 따로 진입점을 만들지 않는다.

#### 발행물 종류

| 종류 | 형식 | 주기 | 상태 |
|---|---|---|---|
| 일간 신문 | 카드뉴스 | 매일 | 나중에 기획 |

  → Playwright(Chromium) 렌더링
  → PDF 출력
  → Supabase Storage 업로드
  → 앱 뷰어로 열람

- 파일명 ASCII only

| 구분 | 용도 | 사양 | 접근 |
|---|---|---|---|
| **digital** | 앱 내 열람, 다운로드 | 10인치 태블릿 쾌적 수준 (약 150DPI) | 유저 접근 가능 |

> 디지털 발행물을 "충분히 좋지만 인쇄하면 아쉬운" 수준으로 제한해 실물 구독의 가치를 보호한다. 동일 HTML 템플릿에서 두 프로필을 뽑으므로 유지보수 부담이 없고, 디지털 발행물을 만드는 순간 실물 발행 준비가 자동 완료된다.

**A4 비율 트레이드오프**: 모바일에서 글자가 작아지는 불편은 감수한다. 그 레이아웃이 그대로 실물 인쇄로 이어지므로 이중 작업이 없고, 실물 출판 구독이라는 수익원의 명분이 된다.

## Part 10. 연애 유형 추론 · 궁합 · 온도 산출 시스템

> 화면 4의 전체 명세. MBTI 16유형 × 5문항 = 총 80문항, 각 3지선다.
> **결정론 계약**: 동일 MBTI + 동일 응답 = 항상 동일 결과.


### 10-1. 설계 원리

#### 10-1-1. 왜 5문항으로 가능한가

MBTI를 이미 알고 있다는 전제에서, 5문항은 "MBTI가 알려주지 않는 정보"만 캐내면 된다. 그 잔여 정보가 정확히 무엇인지 심리측정 연구로 특정했다.

**근거 ① — MBTI는 빅5 중 4개를 이미 담고 있다**

McCrae & Costa(1989), Furnham(1996) 등의 연구에서 확인된 상관:

| MBTI 축 | 빅5 요인 | 상관계수 |
|---|---|---|
| I ↔ E | 외향성(Extraversion) | r = -0.74 (강함) |
| N ↔ S | 개방성(Openness) | r = 0.72 (강함) |
| F ↔ T | 우호성(Agreeableness) | r = 0.44 (중간) |
| P ↔ J | 성실성(Conscientiousness) | r = -0.49 (중간) |
| **— (없음)** | **신경성(Neuroticism)** | **MBTI 어떤 척도와도 무상관** |

→ **결론: 빅5 중 신경성만 직접 물어보면 된다.** 나머지 4개는 MBTI에서 사전확률로 도출하고, 후술할 Q1·Q2 응답으로 미세보정한다.

**근거 ② — 애니어그램은 두 삼분법의 교차로 유일하게 결정된다**

리소-허드슨 체계의 두 삼분법은 서로 직교한다.

- **호나이 삼분법**(사회적 전략): 주장형(3·7·8) / 순응형(1·2·6) / 후퇴형(4·5·9)
- **하모닉 삼분법**(좌절 대처): 역량형(1·3·5) / 긍정형(2·7·9) / 감정반응형(4·6·8)

교차표를 그리면 9칸 각각에 정확히 한 유형씩 배정된다:

| | 역량형(1·3·5) | 긍정형(2·7·9) | 감정반응형(4·6·8) |
|---|---|---|---|
| **주장형**(3·7·8) | **3** | **7** | **8** |
| **순응형**(1·2·6) | **1** | **2** | **6** |
| **후퇴형**(4·5·9) | **5** | **9** | **4** |

→ **결론: 2문항(호나이 1문항 + 하모닉 1문항)으로 애니어그램 코어 9유형이 결정론적으로 확정된다.** 확률 추론이 아니라 룩업 테이블이므로 재현성 100%.

**근거 ③ — 스턴버그 삼각이론은 독립 구인이다**

친밀(Intimacy)·열정(Passion)·헌신(Commitment)은 성격이 아니라 **관계 행동** 구인이라, MBTI/애니어그램에서 파생되지 않는다. 별도 문항 1개 필요.

원 척도(STLS)는 각 성분 15문항씩 총 45문항이지만, MVP에서는 "어느 성분이 우세한가"만 판별하면 되므로 1문항 3지선다로 압축한다. (정밀 측정이 아니라 프로파일 분류가 목적)

**근거 ④ — 애착 유형은 2축 교차로 결정된다**

애착 이론의 표준 2차원 모델(불안 축 × 회피 축)을 사용한다. 불안 축은 신경성 문항(Q3)과 사실상 같은 구인이므로 **공유**하고, 회피 축만 별도 문항(Q5)으로 측정한다.

| | 회피 낮음 | 회피 높음 |
|---|---|---|
| **불안 낮음** | 안정형 | 회피형 |
| **불안 높음** | 불안형 | 혼란형 |

#### 10-1-2. 5문항 슬롯 구조 (16유형 공통 골격)

문항이 측정하는 **구인은 16유형 모두 동일**하고, **시나리오·표현만 유형별로 커스텀**한다. 이렇게 하는 이유:

1. **표면타당도 상승** — "이 질문 나한테 딱 맞네"라는 몰입감
2. **변별력 상승** — 해당 유형이 실제로 마주치는 상황으로 물으니 응답이 선명해짐
3. **결정론 유지** — 구인과 채점 규칙은 동일하므로 재현성 보장

| Q# | 측정 구인 | 선택지 | 산출물 |
|---|---|---|---|
| **Q1** | 호나이 삼분법 (욕구 충족 전략) | 3 | 애니어그램 후보 3개로 압축 + 빅5 우호성 보정 |
| **Q2** | 하모닉 삼분법 (좌절 대처) | 3 | Q1과 교차 → **애니어그램 코어 확정** + 빅5 성실성 보정 |
| **Q3** | 신경성 (빅5 N) = 애착 불안 축 | 3 | 빅5 신경성 확정 + 애착 불안 축 |
| **Q4** | 스턴버그 우세 성분 | 3 | 친밀/열정/헌신 프로파일 |
| **Q5** | 애착 회피 축 | 3 | Q3와 교차 → **애착 유형 확정** |

**정보량**: 3⁵ = 243 응답 패턴 × MBTI 16유형 = 3,888가지 입력 조합
**최종 라벨**: 애니어그램 코어(9) × 애착 유형(4) = **36종 연애 유형**

#### 10-1-3. 선택지 의미 규격 (전 유형 공통 — 채점의 기준)

시나리오는 유형별로 다르지만, 각 선택지가 가리키는 값은 아래로 고정된다.

**Q1 — 호나이 삼분법**
| 선택지 | 값 | 의미 |
|---|---|---|
| A | 주장형 (Assertive) | 내가 먼저 움직여 상황을 만든다 |
| B | 순응형 (Compliant) | 해야 할 도리·역할을 다하며 얻는다 |
| C | 후퇴형 (Withdrawn) | 일단 물러나 내 안에서 정리한다 |

**Q2 — 하모닉 삼분법**
| 선택지 | 값 | 의미 |
|---|---|---|
| A | 역량형 (Competency) | 감정은 접어두고 문제부터 해결 |
| B | 긍정형 (Positive Outlook) | 좋은 쪽으로 해석하고 넘어간다 |
| C | 감정반응형 (Reactive) | 감정을 그대로 드러내고 진짜 반응을 요구 |

**Q3 — 신경성 / 애착 불안**
| 선택지 | 값 | 의미 |
|---|---|---|
| A | 낮음 | 웬만해선 흔들리지 않고 금방 넘어간다 |

**Q4 — 스턴버그 우세 성분**
| 선택지 | 값 | 의미 |
|---|---|---|
| A | 친밀 (Intimacy) | 편안함, 통하는 느낌, 속마음 공유 |
| B | 열정 (Passion) | 설렘, 끌림, 강렬함 |

### 10-5. 연애 유형 36종 라벨 (확정)

애니어그램 코어(9) × 애착 유형(4) = 36종. **3단 표기 체계**를 쓴다.

| 용도 | 표기 | 예시 |
|---|---|---|
| **코드** | 3자 약어 (DB·API 기본 키) | `MSF` |
| **영문 라벨** | 조어 (공유 카드 헤드) | `MUSEFLARE` |
| **한글 라벨** | 서술형 (카드 본문) | 열대야 같은 낭만주의자 |
| **카피** | 한 줄 설명 | 사랑 때문에 잠 못 드는 사람 |

#### 10-5-1. 조어 체계

**구조: [코어] + [온도 상태]**

서비스명 ONDOLOG(온도 + 로그)에 맞춰, 애착 유형을 **"그 사람이 사랑할 때의 기후"**로 표현한다. 메인 탭의 연애 온도(36.5도)와 같은 언어를 쓰므로 세계관이 일관된다.

**코어 (애니어그램 9종)**

| # | 코어 | 약어 | 어원 | 선정 이유 |
|---|---|---|---|---|
| 1 원칙 | **KEEL** | KL | 배의 용골 | 흔들려도 중심을 잡아주는 구조물 |
| 2 조력 | **BALM** | BL | 연고, 진정제 | 상처에 발라주는 것 |
| 3 성취 | **APEX** | AX | 정점 | 올라가야 직성이 풀림 |
| 4 낭만 | **MUSE** | MS | 뮤즈, 영감 | 감정을 예술로 바꾸는 사람 |
| 5 탐구 | **LORE** | LR | 축적된 지식 | 관찰하고 쌓아두는 사람 |
| 6 충실 | **OATH** | OT | 맹세 | 한번 한 약속은 끝까지 |
| 7 열정 | **RUSH** | RH | 짜릿함, 돌진 | 새로움을 향해 달림 |
| 8 도전 | **IRON** | IN | 강철 | 단단하게 지켜냄 |
| 9 중재 | **LULL** | LL | 잔잔함, 소강 | 파도가 가라앉은 상태 |

**접미사 (애착 4종)**

| 애착 | 접미사 | 약어 | 의미 |
|---|---|---|---|
| 안정 (secure) | **-EMBER** | **E** | 잉걸불 — 은은하게 오래 탄다 |
| 불안 (anxious) | **-FLARE** | **F** | 화염 — 확 타오른다 |
| 회피 (avoidant) | **-FROST** | **S** | 서리 — 서늘하게 아름답다 |
| 혼란 (fearful) | **-TIDE** | **T** | 조수 — 밀려왔다 밀려간다 |

> **약어 설계 근거 2가지**
> ① FLARE와 FROST가 둘 다 F로 시작해 충돌하므로 FROST에 `S`를 배정했다. **F(뜨거움) ↔ S(차가움)** 대비가 한눈에 읽힌다.
> ② 코어 약어는 앞 두 글자가 아니라 **자음 골격**(K—L, M—S)을 쓴다. 앞 두 글자로 자르면 `APE`(원숭이) · `OAF`(멍청이) · `IRE`(분노) · `RUE`(후회) 같은 조합이 나온다. 자음 골격에서는 실제 단어와 겹치는 게 `AXE` 하나뿐이고 그건 무해하다.

**엘리전 규칙**: E로 끝나는 코어(MUSE, LORE)는 `-EMBER`와 만날 때 E를 하나 흡수한다 → `MUSEMBER`, `LOREMBER`

#### 10-5-2. 36종 전체

**1. KEEL — 원칙주의자**

| 애착 | 코드 | 영문 | 한글 | 카피 |
|---|---|---|---|---|
| 안정 | `KLE` | KEELEMBER | 온돌 같은 원칙주의자 | 늘 같은 온도로 곁에 있는 사람 |
| 불안 | `KLF` | KEELFLARE | 달아오르는 원칙주의자 | 잘하고 싶어서 혼자 뜨거워지는 사람 |
| 회피 | `KLS` | KEELFROST | 새벽 같은 원칙주의자 | 아무도 없는 시간에 기준을 지키는 사람 |

### 10-6. 궁합 매트릭스

#### 10-6-0. 전제 — 이 표는 운명이 아니다

애니어그램 이론의 공식 입장은 **"특별히 축복받은 조합도, 특별히 저주받은 조합도 없다"**이다. 애니어그램 인스티튜트(리소-허드슨 체계의 본산)는 유형 조합표란 두 사람 사이에 생기기 쉬운 주요 쟁점을 이해하기 위한 개요일 뿐이며, 두 사람이 건강하다면 어떤 유형과도 관계를 맺을 수 있다고 명시한다.

실제로 시중의 궁합표들은 서로 정면으로 모순된다. 어떤 자료는 6번의 최고 궁합이 9번이라 하는데 다른 자료는 9번의 최악 궁합이 6번이라 한다. 같은 조합(1·7)이 한쪽에서는 강한 조합으로, 다른 쪽에서는 규율 대 즉흥성의 충돌로 분류된다. **합의된 정답이 없다.**

따라서 이 매트릭스의 성격을 다음과 같이 규정한다.

| 이 표는 | 이 표는 아니다 |
|---|---|
| 각 조합에서 어떤 쟁점이 생기기 쉬운지 미리 아는 안내 | 누구와 사귀어야 하는지 알려주는 지침 |
| 이미 알고 있으면 대비할 수 있는 참고 자료 | 관계의 성패를 예측하는 도구 |
| 정통 이론(삼분법·화살표)에서 도출한 구조적 경향 | 통계적으로 검증된 성공률 |

**화면에도 이 취지가 드러나야 한다.** 온도차 섹션 상단에 다음 취지의 문구를 노출한다.

> *"온도차가 있다는 건 안 맞는다는 뜻이 아닙니다.
> 조금 더 신경 쓰면 되는 지점이 있다는 뜻입니다."*

> ⚠️ **구현 시 주의**: 이 문구를 옵션으로 두지 않는다. 궁합 섹션이 렌더링될 때 항상 함께 표시되어야 한다. 이 표가 운명론으로 읽히는 순간, 이미 그 유형과 사귀고 있는 유저에게 상처가 된다.

#### 10-6-1. 명명 — "best/worst"를 쓰지 않는다

화면 7은 **커플 매칭 전, 1인 상태**에서 뜨는 화면이다. 여기서 "worst(최악)"라는 단어를 쓰면 이미 그 유형과 사귀고 있는 유저가 상처받는다. Part 3-7의 톤 원칙(결핍이 아니라 특성으로 프레이밍)과도 어긋난다.

서비스명(온도 + 로그)과 36종 라벨의 기후 메타포에 맞춰 다음과 같이 명명한다.

| 구분 | 표기 | 의미 |
|---|---|---|
| best | **온도가 잘 맞는 유형** | 자연스럽게 통하는 조합 |
| worst | **온도차가 있는 유형** | 노력이 필요한 조합. 나쁜 게 아니라 다른 것 |

"온도차가 있다"는 사실을 정직하게 말하되 판정하지 않는다. 각 항목에는 **반드시 실행 팁을 함께 제공**한다.

#### 10-6-2. 산출 근거 — 3가지 구조

매트릭스는 임의로 정하지 않는다. 이미 5문항 채점에 사용 중인 애니어그램 구조에서 도출한다.

**① 호나이 삼분법 (사회적 전략)**

| 그룹 | 유형 | 전략 |
|---|---|---|
| 주장형 | 3 · 7 · 8 | 내가 나서서 만든다 |
| 순응형 | 1 · 2 · 6 | 해야 할 도리를 다한다 |
| 후퇴형 | 4 · 5 · 9 | 물러나서 내 안에서 해결한다 |

**② 하모닉 삼분법 (좌절 대처)**

| 그룹 | 유형 | 대처 |
|---|---|---|
| 역량형 | 1 · 3 · 5 | 감정을 접고 문제부터 |
| 긍정형 | 2 · 7 · 9 | 좋은 쪽으로 재해석 |
| 반응형 | 4 · 6 · 8 | 감정을 그대로 드러냄 |

**③ 화살표 (성장·스트레스 방향)**

| 방향 | 경로 |
|---|---|
| 통합(성장) | 1→7, 2→4, 3→6, 4→1, 5→8, 6→9, 7→5, 8→2, 9→3 |
| 분열(스트레스) | 1→4, 2→8, 3→9, 4→2, 5→7, 6→3, 7→1, 8→5, 9→6 |

**도출 규칙**

| 규칙 | 판정 |
|---|---|
| R1 | 다른 호나이 + 같은 하모닉 → 역할은 다르고 대처는 통한다 → **잘 맞음** |
| R2 | 통합 화살표 상대 → 내가 성장하는 방향의 자질을 가진 사람 → **잘 맞음** |
| R3 | 긍정형이 섞인 조합 → 갈등의 완충재 역할 → **잘 맞음** |
| W1 | 반응형끼리(4·6·8) → 감정 증폭, 갈등 에스컬레이션 → **온도차** |
| W2 | 주장형끼리(3·7·8) → 주도권 충돌 → **온도차** |
| W3 | 후퇴형끼리(4·5·9) → 아무도 먼저 다가가지 않음 → **온도차** |
| W4 | 같은 호나이 + 다른 하모닉인데 욕구 방향이 어긋남 → **온도차** |

#### 10-6-3. 온도차 관계는 대칭, 잘 맞는 관계는 비대칭

**온도차는 반드시 상호적으로 설계했다.** A가 B를 "온도차"라 하는데 B는 A를 "잘 맞음"이라 하면, 커플이 서로의 결과를 비교했을 때 한쪽이 상처받는다.

반면 **잘 맞는 관계는 비대칭을 허용한다.** 애니어그램 화살표가 방향성을 갖기 때문이다. 예를 들어 2는 4를 향해 성장하지만(2→4), 4는 1을 향해 성장한다(4→1). 그래서 2의 목록에는 4가 있지만 4의 목록에는 2와 1이 함께 있다.

이 비대칭 자체가 콘텐츠가 된다 — "관계는 서로 다른 이유로 끌린다"는 서술이 가능하다.

#### 10-6-4. 온도차 관계 9쌍 (전체)

9개 유형이 하나의 순환 고리를 이룬다.

```
1 — 8 — 7 — 3 — 2 — 5 — 9 — 4 — 6 — 1
```

| 쌍 | 규칙 | 이유 |
|---|---|---|
| 1 · 8 | W4 | 원칙 대 힘. 1은 옳음으로, 8은 강함으로 상황을 통제하려 한다 |
| 8 · 7 | W2 | 주장형끼리. 둘 다 앞으로만 가려 해서 멈춰 서서 맞출 시간이 없다 |
| 7 · 3 | W2 | 주장형끼리. 속도와 성과를 겨루다 관계 자체가 뒤로 밀린다 |
| 3 · 2 | W4 | 같은 인정 욕구인데 방향이 다르다. 3은 성취로, 2는 관계로 인정받고 싶어 한다 |
| 2 · 5 | W4 | 돌봄 대 거리. 2의 다가감이 5에게는 침범으로 느껴진다 |
| 5 · 9 | W3 | 후퇴형끼리. 둘 다 물러나서 아무도 먼저 화해를 꺼내지 않는다 |
| 9 · 4 | W3 | 후퇴형끼리인데 9는 갈등을 피하고 4는 감정을 요구한다 |
| 4 · 6 | W1 | 반응형끼리. 한쪽의 불안이 다른 쪽의 감정을 자극해 증폭된다 |
| 6 · 1 | W4 | 같은 순응형. 둘 다 불안을 규칙으로 다스리려다 서로의 긴장을 키운다 |

### 10-7. 연애 온도 계산 규격 (확정)

> **이 절이 온도 계산의 원본이다.** Part 9-2는 표시 규격만 보유하며 이 절을 가리킨다.
> `engine-dev` 참조 범위 안에 두기 위해 Part 10에 배치했다 — 온도의 기저가
> 10-6 궁합 매트릭스이므로 위치도 자연스럽다.

#### 10-7-1. 구조

연애 온도는 성격 프로파일을 입력으로 사용한다. **기저 + 변동** 구조다.

```
temperature = clamp(baselineTemperature + activityDelta, 0, 100)
```

| 식별자 | 의미 | 갱신 |
|---|---|---|
| `temperature` | 일간 최종 온도 (메인 탭 표시값) | 일 단위 배치 |
| `baselineTemperature` | 성격 기반 기저 온도 | 커플별 고정 |
| `activityDelta` | 활동 변동분 | 일 단위 배치 |
| `typeAffinity` | 유형 궁합 범주 (10-6-5) | 고정 |

> **식별자 규칙**: `typeAffinity`만 다른 어근을 쓴다. 온도 계열 어근
> (`temperature`)을 유형 궁합에 쓰지 않으며, 반대도 같다. 나머지 셋은 같은
> 계산 체계라 어근을 공유한다. 격리 컨텍스트에서 시작하는 서브에이전트는
> "온도"라는 한글 단어 하나로 두 개념을 구분할 수 없다.

#### 10-7-2. 기저 온도

```
baselineTemperature = 36.5 (온도차) | 39 (중립) | 42 (잘 맞음)
```

- `typeAffinity` 범주는 **Part 10-6-5 유형별 매트릭스**에서 가져온다.
  잘 맞는 유형 목록에 있으면 "잘 맞음", 온도차 목록에 있으면 "온도차",
  **어느 목록에도 없으면 중립**이다.
- 10-6-3에 따라 온도차 관계는 대칭이지만 잘 맞는 관계는 비대칭이다.
  **양방향 판정이 어긋나면 높은 쪽을 커플 기저로 삼는다.**
- **기저는 36.5 아래로 내려가지 않는다.**
- 양측 성격 프로파일이 모두 갖춰지기 전에는 기저를 산출하지 않는다.
- 일간 배치에서 재계산하지 않는다.

> **왜 하한이 36.5인가.** 36.5는 "아직 아무 데이터도 없는 평온한 기본 체온"으로
> 정의돼 있다. 기저가 그 아래로 내려가면 연결한 뒤가 혼자일 때보다 낮아지고,
> 그 원인이 상황이 아니라 성격이라 상황·맥락에 귀속시킬 수 없다.
> Part 3-7 원칙 ①과 10-6-0("이 표는 운명이 아니다")에 정면으로 걸린다.

#### 10-7-3. 활동 변동분

```
activityDelta = (최근 14일 활동 점수 합) / 14 × 55     상한 55, 하한 0
```

- 이동창 **14일 고정**.
- **창이 차기 전에도 분모는 항상 14**이며, 없는 날은 0으로 계산한다.
  가입 초기에 계산 방식이 바뀌지 않으며, 신규 커플은 기저에서 출발해
  활동이 쌓이는 만큼 올라가는 상승 곡선을 본다.
- 최종 온도는 `activityDelta` 감소로 36.5 아래까지 내려갈 수 있다.
  **활동 기반 하락은 허용된다** — "요즘 바빴다"로 귀속 가능한 종류다.
  막는 것은 성격에서 오는 하락뿐이다.

**미확정** — 하루치 활동 점수의 정의(채팅·피드 건수 → 점수)는 실사용
데이터 없이 정하면 근거 없는 값이 된다. `UNRESOLVED('temperature.activityScore')`로
두고 캘리브레이션 항목으로 넘긴다. Part 16-2에 등재.

#### 10-7-4. 폭 배분 근거

| | 기저 폭 | 활동 폭 |
|---|---|---|
| 값 | 36.5 / 39 / 42 (차이 5.5) | 0 ~ 55 |

기저 차이를 작게 잡은 이유는 **성격 폭이 클수록 원칙 ① 위험이 커지기**
때문이다. 기저 격차가 크면 온도차 커플은 아무리 노력해도 천장이 낮고,
그 원인이 유저가 바꿀 수 없는 성격이다. 현재 배분에서는 **2주만 꾸준해도
기저 차이가 뒤집힌다.**

활동 폭 55를 14로 나누므로 하루치는 최대 4점 남짓이다. 하루 조용하면
소수점대로 움직이고, 2주가 통째로 조용해야 뚜렷하게 내려온다.
넓은 대역에서 정수 단위 급락이 구조적으로 발생하지 않는다.

#### 10-7-5. 계수 관리와 재현성

**모든 임계값·가중치는 매개변수다.** 위 숫자를 상수로 하드코딩하지 않는다.

| 항목 | 규칙 |
|---|---|
| 계수 출처 | `app_config`에서 읽고 **호출부가** 인자로 주입 |
| 엔진 함수 | 계수를 **인자로만** 받는다. `src/engine/` 하위에서 DB·네트워크·환경변수 접근 금지 |
| 재배포 | 계수 변경은 앱 재배포를 요구하지 않는다 |
| 버전 기록 | 산출 시 `daily_temperature.factors`에 **계수 버전**을 함께 기록 |
| 함께 남길 것 | `baselineTemperature`, `activityDelta`, 활동 원재료 근거 |

> `app_config` 사용은 절대 규칙 2 위반이 **아니다.** 계수가 인자로 들어오는 한
> 함수는 순수하고 동일 입력에 동일 출력이 나온다. 깨지는 것은 함수의
> 결정론이 아니라 **발행물 재현성**이다 — 3월호에 실린 78.4를 6월에
> 재계산했을 때 다른 값이 나오는 문제. 계수 버전 기록이 이를 막는다.
> **버전 기록 없는 산출은 허용하지 않는다.**
>
> ⚠️ 엔진 모듈 안에서 `fetch`나 supabase 클라이언트를 쓰면 함수가 비동기가
> 되고 순수성이 사라진다. 결정론 grep(`Math.random|Date.now|new Date`)에는
> 걸리지도 않는 **조용한 실패**다. 계수 조회는 호출부의 책임이다.

`daily_temperature`에는 `engine_version` 컬럼이 없고 `factors jsonb`만 있으므로
버전을 `factors` 안에 넣는다. `stat_snapshots`와 방식이 다르다(§10-8-3 참조).

#### 10-7-6. 연애 DNA 일치율과의 분리

두 지표는 **성격이라는 재료를 공유하지만 산출물은 서로 참조하지 않는다.**

| | 연애 온도 | 연애 DNA 일치율 |
|---|---|---|
| 성격 | 일 단위 활동 지표 | 월간 지표 |
| 위치 | 메인 탭 | Part 17-2 코너 |

**한쪽 값을 다른 쪽 계산에 입력으로 넣지 않는다.** 공유되는 것은 원천 성격
프로파일까지이며, 산출된 값(`temperature`, DNA 일치율)은 서로 참조하지 않는다.

### 10-8. 규준집단 · OVR 산출 규격 (확정)

#### 10-8-1. 규준집단 — 전수 열거 합성 규준

초기 규준집단은 **응답 공간 전수 열거**로 생성한다.

```
Q1~Q5 각 3지선다 = 3⁵ = 243
× MBTI 16종 = 3,888개 프로파일
```

채점이 전부 결정론적 룩업·산술이므로(10-2), 3,888개 프로파일의 6각 스탯을
**정확히 계산할 수 있다.** 추정이 아니라 열거다. 각 응답 조합은 균등 가중한다.

**베이지안 수축의 사전평균은 이 분포의 스탯별 평균을 쓴다.**

> **17-3 설계 원칙 4를 대체한다.** 기존 문구는 "초기엔 공개 연구 추정치"였으나
> 이는 실행 불가능하다. 6각 스탯(PUS·TAC·REA·DEF·ATT·EMP)은 에니어그램·애착·빅5를
> 자체 공식으로 결합한 **합성 지표**라, 대응하는 공개 규준이 존재하지 않는다.
> 빅5 규준은 있으나 우리 스탯 공식과 매핑되지 않는다.

**잠정값이다.** 실제 유저 분포는 균등하지 않으므로(MBTI만 해도 유형별 빈도가
크게 다르다) 초기 백분위는 왜곡을 포함한다. 17-3 원칙 4의 "유저 누적 시
자사 데이터로 교체" 경로를 그대로 따른다.

#### 10-8-2. OVR 산출

**OVR은 6각 스탯의 산술평균이다(반올림). 포지션별 가중치를 적용하지 않는다.**

기존 처리 순서 4단계에서 ② "포지션별 가중치 적용"을 **삭제**하고 3단계로 한다.

```
① 6개 스탯 원점수 → ② 규준집단 백분위 변환 → ③ 매핑 테이블로 최종 OVR
```

백분위→OVR 매핑 테이블(40~120, 17-3)은 그대로 유지한다.

**연애 포지션은 표시용 라벨로만 남는다.** OVR 계산에 관여하지 않으므로
네이밍 체계는 별도 작업으로 미룬다(Part 16-1). `stat_snapshots.position_code`는
nullable이므로 확정 전까지 null로 둔다.

**검증 조건** — 규준집단 전수 열거 시 **에니어그램 코어 9종별 OVR 분포를
함께 산출한다.** 6각 스탯이 유형에서 도출되므로 특정 유형이 구조적으로
낮은 OVR을 받을 수 있고, 백분위 변환은 순위만 보므로 이를 교정하지 않는다.
특정 유형이 체계적으로 하위 구간에 몰리면 **가중치 도입을 재검토한다.**
이 점검을 규준집단 산출 작업의 완료 기준에 포함한다.

> `src/engine/leagueStats.ts` 현행 구현이 이미 6스탯 단순 평균이므로
> **이 항목의 코드 변경은 없다.** 자리표시자 해제 표시와 테스트 갱신만 필요하다.

#### 10-8-3. 규준 버전 기록

`stat_snapshots`에는 `engine_version text not null`이 이미 있고 `inputs jsonb`도
있으므로 **마이그레이션이 필요 없다.**

| 항목 | 위치 |
|---|---|
| 엔진 코드 버전 | `stat_snapshots.engine_version` |
| 규준집단 버전 | `stat_snapshots.inputs.normVersion` |

**둘을 분리한다.** 엔진 코드는 그대로인데 규준집단만 자사 데이터로 교체하는
상황이 원칙 4에 이미 예정돼 있어, 독립적으로 변한다.
이전 버전으로 산출된 발행물은 그 버전으로 재현 가능해야 한다.

**미확정** — 베이지안 수축 강도 파라미터는 전수 열거 분포의 분산을 관측한 뒤
정한다. `UNRESOLVED('leagueStats.shrinkage')`로 두고 Part 16-2에 등재.

### 15-3. 서브에이전트 운영 시 유의사항

클로드 코드의 서브에이전트는 **CLAUDE.md와 메모리 계층은 상속받지만, 부모의 대화 히스토리는 받지 않는다.** 부모→자식으로 전달되는 유일한 통로는 위임 프롬프트뿐이다.

| 항목 | 지침 |
|---|---|
| 절대 규칙 | CLAUDE.md에 넣으면 **모든 서브에이전트가 자동 상속** → 15-1의 절대 규칙은 반드시 여기 배치 |
| 개별 스펙 | 특정 에이전트만 필요한 정보(화면 스펙 등)는 **위임 프롬프트에 명시적으로 포함** |
| 에이전트 간 조율 | 실시간 메시지 버스 없음. **공유 파일 + 오케스트레이터**로만 가능 → 상태 공유가 필요하면 파일 경로를 규칙으로 정해둘 것 |
| 권장 규모 | 대부분의 워크플로우에 3~5개 서브에이전트. 다수 항목 처리 시 5~10개씩 배치 처리 |
| 모델 믹싱 | 검증·리뷰·문서 작성은 Haiku, 오케스트레이터·아키텍트는 Opus → 비용 40~60% 절감 가능 |

### 15-4. 구현 시 반드시 지킬 것 (연애유형 시스템)

- 채점 로직은 **순수 함수**로 구현하고 단위 테스트를 붙일 것. 동일 입력 → 동일 출력이 계약이다.
- 랜덤·시간 기반·세션 기반 요소를 채점 경로에 절대 넣지 말 것.
- 문항 데이터는 `src/data/onboardingQuestions.ts`에 MBTI 유형별 객체로 분리 관리.
- 채점 로직은 `src/engine/loveTypeInference.ts`에 배치.
- 룩업 테이블은 `src/constants/`에 상수로 분리해 문항과 로직을 디커플링할 것.
- MBTI별 애니어그램 사전분포는 **채점에 관여하지 않는다.** 오직 "희귀 배지" 표시와 선택지 노출 순서에만 사용.

> **미해결 상수 규격.** 미확정 계수는 값이 아니라 `UNRESOLVED(key)`로 선언하고,
> 해당 테스트는 값이 아니라 **throw를 기대하도록** 작성한다. 자리표시자가
> 결정론적이면 테스트를 통과해버려 정확성이 오인된다(실제로 Phase 2에서 발생).
> `UNRESOLVED` 키는 이 목록과 **1:1로 대응한다** — 코드에만 있고 목록에 없는
> 키는 그 자체가 감사 위반이다. Phase 착수 조건에
> `grep -rn "UNRESOLVED" src/engine/` 0건을 걸고 `rule-auditor`에 편입한다.

### 17-1. 데이트 아카이브 (월간)

#### 개념

**하루의 데이트 하나 = 한 편의 기사.** 시간 순서를 따라 그날을 재구성하고, 자동 인식된 데이트 기록에 유저가 남긴 글·그림을 얹어 편집한 뒤, 마지막에 커플이 함께 이야기할 질문을 던진다.

#### 원재료

| 소스 | 내용 |
|---|---|
| 피드 탭 사진 | EXIF 시각·GPS로 클러스터링된 데이트 단위 |
| AI 서사 | 코스 해석 (장소 → 장소 이동 맥락) |
| 유저 보정 | 수정된 장소명, 사진 위 감정 기록·드로잉 |
| 해시태그 | 선택적 입력값 |

#### 지면 구성

| 순서 | 요소 |
|---|---|
| 1 | **헤드** — 날짜, 지역, AI 생성 데이트 제목 |
| 2 | **타임라인 본문** — 장소별 시간순 블록 (사진 + 유저 글/그림 + AI 캡션) |
| 3 | **마무리 질문 3개** |

**타임라인 블록 예시**

```
14:20 · 홍대 CGV
[사진 1~2장]
"스파이더맨 봤다. 서영이는 중간에 졸았음"   ← 유저가 쓴 글
[유저가 그린 그림]

16:40 · OO식당
[사진]
영화 끝나고 근처에서 저녁                    ← AI 캡션 (유저 기록 없는 구간)

18:30 · 연남동 OO카페
[사진 2~3장]
"여기 케이크 진짜 맛있었어"                  ← 유저 기록
```

**AI의 역할**: 시간·장소 정렬, 유저 기록이 없는 구간에 한 줄 캡션 채우기, 전체를 하나의 서사로 다듬기. **유저 기록이 있으면 그게 주인공이고 AI는 물러난다.**

#### 마무리 질문

| 유형 | 예시 | 성격 |
|---|---|---|
| 평점형 | 이날의 데이트는 10점 만점에 몇 점? | 고정 질문 |
| 회상형 | 이날 중 가장 기억에 남는 건? | 고정 질문 |
| **맞춤 제안형** | 다음에 롯데월드 갈 때 교복 데이트 해볼 의향은? | **AI가 그날 데이터 기반 생성** |

**답변 처리: 기록하지 않음**

| 항목 | 내용 |
|---|---|
| 저장 | **없음** — 앱에 입력받지 않음 |
| 목적 | **순수 대화 유도** — 잡지를 함께 보며 오프라인에서 이야기하게 만드는 장치 |
| 구현 이점 | PDF 위 인터랙션 레이어 불필요 |

> ONDOLOG는 앱 사용 시간을 늘리는 게 아니라 관계의 온도를 높이는 게 목적이다. 질문의 답은 앱이 아니라 두 사람 사이에 남는 게 맞다.
> 맞춤 제안형은 잡지를 과거 기록에서 끝내지 않고 **미래 행동으로 연결**하는 리텐션 장치다.

#### 선별 로직 (한 달 데이트가 많을 때)

1. 사진 수가 많은 데이트 (인상적이었다는 신호)
2. 유저가 감정 기록·드로잉을 남긴 데이트 (직접 개입 = 의미 부여)
3. 새로운 지역 방문 (반복 코스보다 새로움)
4. 오래 머문 데이트 (EXIF 시각 폭이 넓은 것)

#### 데이터 부족 시 — "그때 그 시절" 재소환

| 조건 | 동작 |
|---|---|
| 이번 달 3건 이상 | 정상 발행 |
| 1~2건 | 과거 데이트 1~2건 재소환으로 보완 |
| 0건 | 전부 과거 데이트로 구성 |

**재소환 기준**: ① 기념일 근접(1년 전 오늘) ② 미발행 과거 데이트 우선 ③ 재등장 최소 6개월 간격
**표기**: 재소환 데이트에 "그때 그 시절" 배지

### 17-2. 우리의 연애 DNA (월간)

#### 개념

두 사람의 성격 프로필을 결합해 관계의 궁합과 역학을 분석하는 코너. 매거진의 헤드라인이자 가장 진지한 톤을 담당한다. 연애리그가 "게임적 재미"라면 이쪽은 "진짜 분석"이다.

#### 일치율 로직 — 성격 기반 + 채팅 변동성

| 구성 | 성격 |
|---|---|
| **성격 기반 점수** | 5문항 산출값(빅5·애니어그램·스턴버그·애착) 조합 — 변하지 않는 기저 |
| **채팅 반영 변동분** | 앱 내 채팅의 양·질(다정한 발화 빈도, 응답 리듬, 티키타카 성공률)이 점수를 움직임 |

**이 구조의 3가지 이점**

1. **매호 실을 이유가 생김** — 숫자가 매달 달라지므로 지루해지지 않음
2. **채팅 탭 사용 유도** — 앱 내에서 대화해야 점수가 움직이니 카톡 대신 ONDOLOG를 쓸 동기 발생
3. **데이터 파이프 강화** — 채팅이 늘수록 모든 코너의 원재료가 풍부해짐

> ⚠️ **양이 아니라 질에 가중치.** 채팅량만으로 점수가 오르면 의미 없는 도배를 유발한다. 다정한 발화 비율, 대화 왕복의 자연스러움에 비중을 둘 것.

#### 절대평가 (상대평가 폐지)

| 항목 | 처리 |
|---|---|
| 규준집단 백분위 | **미적용** |
| "상위 몇 %" 표기 | **삭제** |
| 산출 방식 | **절대평가** — 이 커플의 데이터만으로 산출 |

> 다른 커플과 비교하는 순간 관계가 경쟁이 된다. ONDOLOG의 목적은 순위 매기기가 아니라 온도 유지다.
> **연애리그와의 구분**: 연애리그 OVR은 규준집단 백분위 기반(상대평가)을 유지한다. 게임적 재미가 목적이라 상대평가가 맞다. **연애 DNA만 절대평가.**

#### 점수 범위 및 톤

| 점수 구간 | 프레이밍 | 추가 요소 |
|---|---|---|
| 60점 초과 | 강점 중심 서술 | — |
| **60점 이하** | **"보완형 조합"으로 프레이밍** | **점수를 올리는 실행 팁 제공** |

**실행 팁 예시**: "채팅을 나눌 때 다정한 한 마디를 더해보세요", "상대의 메시지에 이모지로 반응해보세요"

> 낮은 점수를 "안 맞는다"는 판정이 아니라 **올릴 수 있는 여지**로 바꾼다. 점수가 채팅으로 실제 움직이는 구조라 팁이 빈말이 아니라 검증 가능한 조언이 된다.

#### 지면 구성

| 순서 | 요소 |
|---|---|
| 1 | 헤드라인 — 이달의 일치율 (전월 대비 증감) |
| 2 | 두 사람의 유형 대조 |
| 3 | 빅5 5축 비교 시각화 |
| 4 | 스턴버그 삼각형 겹침 |
| 5 | 애착 조합 해설 |
| 6 | 강점 / 보완 지점 |
| 7 | (60점 이하 시) 점수를 올리는 실행 팁 |

> 📌 **연애 온도와 혼동 금지.** 연애 온도(메인 탭)는 일 단위로 변하는 활동 지표, 연애 DNA 일치율은 성격 기반 + 채팅 변동의 월간 지표다.

### 17-3. 연애리그 시뮬레이션 (주간 + 월간)

#### 개념

피파 얼티밋팀 카드를 오마주한 **개인 스탯 카드 + 커플 매치 리포트** 2단 구조. 주간은 결과, 월간은 해설.

| 구분 | 주간판 | 월간판 |
|---|---|---|
| **컨셉** | 이번 주 경기 결과 | 시즌 리뷰 + 선수 분석 |
| **핵심 질문** | "이번 주 우리는 어땠나" | "왜 이렇게 변했나" |
| **데이터 범위** | 1주치 | 4~5주치 누적 |
| **분량** | 스코어보드 1~2면 | 분석 기사 3~4면 |

#### 6각 스탯 — 5문항 시스템 기반 (재설계 확정)

이전 기획안의 "5분 인터뷰" 전제를 폐기하고, ONDOLOG의 5문항 산출값(빅5 / 애니어그램 코어 / 스턴버그 / 애착)만으로 재구성했다.

| 스탯 | 이름 | 입력 변수 |
|---|---|---|
| **PUS** | 연애 추진력 | 외향성 E(0.4) + 애니어그램 주장형 보너스(3·7·8, 0.3) + 스턴버그 열정(0.3) |
| **EMP** | 감정 공감력 | 우호성 A(0.4) + 애착 안정성(0.3) + 스턴버그 친밀(0.3) |
| **ATT** | 질투·집착력 | 신경성 N(0.4) + 애착 불안축(0.35) + 애니어그램 반응형 보너스(4·6·8, 0.25) |
| **DEF** | 멘탈 회복력 | 정서안정성(100−N)(0.4) + 애니어그램 긍정형 보너스(2·7·9, 0.3) + 애착 안정성(0.3) |
| **TAC** | 밀당 지능 | 개방성 O(0.35) + 애니어그램 후퇴형 보너스(4·5·9, 0.3) + 스턴버그 열정/헌신 비율(0.35) |
| **REA** | 현실 타협력 | 성실성 C(0.5) + 스턴버그 헌신(0.3) + 애니어그램 역량형 보너스(1·3·5, 0.2) |

**애니어그램 보너스 산출 — 삼분법 그룹 소속 0/1 처리**

```
호나이 삼분법 (5문항 Q1에서 직접 도출)
  주장형(3,7,8) → PUS +
  후퇴형(4,5,9) → TAC +

하모닉 삼분법 (5문항 Q2에서 직접 도출)
  역량형(1,3,5) → REA +
  긍정형(2,7,9) → DEF +
  반응형(4,6,8) → ATT +
```

> 5문항 Q1·Q2가 각각 호나이·하모닉을 측정하므로 이 보너스는 **문항 응답에서 직접 도출**된다. 별도 추론 단계가 없어 결정론이 완벽히 보장된다.

**애착 축 수치화**

```
애착 불안축 = Q3 응답 → {A: 20, B: 50, C: 85}
애착 회피축 = Q5 응답 → {A: 20, B: 50, C: 85}
애착 안정성 = 100 − (불안축 + 회피축) / 2
```

**설계 원칙 (계승)**

1. 스탯마다 **3개 독립 소스** 결합 — 단일 축 의존 금지
2. **베이지안 수축(shrinkage) 보정** — 5문항은 정보량이 적으므로 극단값을 모집단 평균 쪽으로 당김
3. **카톡/채팅 2단계 갱신** — 사전확률(5문항) → 사후확률(실측 채팅 데이터). 채팅 없어도 산출 가능
4. **규준집단 정규화** — 초기엔 **전수 열거 합성 규준**(3,888개 프로파일), 유저 누적 시 자사 데이터로 교체. **산출 규격은 Part 10-8-1이 원본.**
   ⚠️ 이전 문구 "초기엔 공개 연구 추정치"는 실행 불가능하여 대체됐다 — 6각 스탯이 자체 정의 합성 지표라 대응 규준이 없다.

#### OVR 캘리브레이션 (계승)

**만점 120점, 비대칭 우측 꼬리 분포**

| 백분위 | 비율 | OVR 구간 | 성격 |
|---|---|---|---|
| 0~10% | 10% | 40~70 | 하위권 |
| 10~80% | **70%** | **70~90** | 메인 구간 |
| 80~95% | 15% | 90~100 | 상위권 |
| 95~99% | 4% | 100~110 | 희귀 |
| 99~100% | 1% | 110~120 | 레전드급 |

**처리 순서 (확정, 3단계)**: ① 6개 스탯 원점수 → ② 규준집단 백분위 변환 → ③ 매핑 테이블로 최종 OVR

> ⚠️ 기존 ② "연애 포지션별 가중치 적용"은 **삭제됐다.** OVR은 6각 스탯의
> 산술평균(반올림)이며 포지션 가중치를 쓰지 않는다. 근거와 검증 조건은 **Part 10-8-2** 참조.

> **설계 의도**: 평균을 후하게(70~90에 70% 몰림) 잡아 낮은 점수로 인한 상처를 최소화하고, 최상위(110~120)만 극희소하게 남겨 "레전드"급 희소성 연출. 당근마켓 매너온도의 하위권 낙인 완화 원칙 계승.

#### 주간판 구성

**① 스탯 카드 공개**

| 요소 | 내용 |
|---|---|
| OVR | 이번 주 오버롤 (지난주 대비 ▲2 / ▼1 증감 표시) |
| 6각 스탯 | 레이더 차트 + 각 수치 (증감 표시) |
| 연애 포지션 | **표시용 라벨.** OVR 계산에 관여하지 않는다 (Part 10-8-2). 네이밍 체계 미확정 — 확정 전까지 `position_code`는 null |

**② 매치 리포트 11개 항목**

| 축구 용어 | 연애 버전 | 산출 로직 |
|---|---|---|
| 점유율 | 예상 대화 점유율 | 양측 PUS + **실제 채팅 발화량** |
| 유효슈팅 | 드립 유효슈팅 | 개방성 대비 상대 EMP |
| 패스 성공률 | 티키타카 성공률 | 양측 EMP 매칭도 + **실제 대화 왕복** |
| 파울 | 대화 태클 | ATT 높은 쪽 마찰 유발 |
| 옐로카드 | 삐짐 옐로카드 | DEF 낮은 쪽, 서운함 스택 연동 |
| 최종 스코어 | 연애 주도권 스코어 | TAC 격차 |
| 교체 | 밀당 타이밍 체인지 | TAC 지수 |
| 극장골 | 막판 감동 극장골 | DEF 높은 쪽의 화해 주도 확률 |
| VAR 판독 | 오해 판독 VAR | 낮은 EMP + 높은 신경성 |
| 어시스트 | 리액션 어시스트 | 개방성 + 외향성 |
| 오프사이드 | 타이밍 오프사이드 | TAC 낮은 쪽의 타이밍 미스 |

> **이전 기획안 대비 핵심 변화**: 이전에는 11개 항목이 전부 성격 벡터만으로 산출됐지만, ONDOLOG는 **채팅 탭 실측 데이터**가 있다. 점유율·티키타카·어시스트 등은 실제 대화 로그로 계산되어 "진짜 우리 얘기"가 된다.

**검토했으나 미채택**: 손절 레드카드(이별 연상 리스크), 무갈등 클린시트, MOM, 홈그라운드 버프

#### 월간판 구성

**① 시즌 종합** — 4~5주치 매치 결과 요약(승/무/패 또는 주도권 추이), 종목별 월간 누적, 시즌 하이라이트

**② 스탯 변동 해설 (월간판의 핵심)**

주간에 보여준 ▲▼ 화살표의 **이유를 서사로 풀어주는** 파트.

> 예시
> **EMP 62 → 71 (▲9)**
> 3주차에 서운함을 먼저 말한 대화가 있었고, 그 이후 티키타카 성공률이 눈에 띄게 올랐습니다. 감정을 꺼내는 임계값이 낮아진 것이 EMP 상승의 주요인입니다.

**③ 능력치 배분표** — 6각 스탯 각각이 어떤 입력값에서 왔는지 투명 공개

| 스탯 | 구성 | 기여도 |
|---|---|---|
| REA 97 | 성실성 82 / 헌신 91 / 역량형 보너스 | 성실성이 절반 |

> "왜 내가 이 점수인지" 납득시키는 장치이자, 결과를 신뢰하게 만드는 근거.

#### MVP 발행 정책 — 압축 시뮬레이션

| 구분 | 정책 |
|---|---|
| **MVP (검증용)** | **압축 시뮬레이션** — 매일 발행하되 하루를 한 주차로 취급. 5일이면 월간판(변동 해설 포함) 생성까지 검증 가능 |
| **정식 운영** | **실제 주기** — 주간판 주 1회, 월간판 월 1회 |

```
publishConfig = {
  mode: 'compressed' | 'production',
  compressionRatio: 1,               // MVP: 1일 = 1주차
  weeklyTrigger: 'daily',            // 정식: 'weekly'
  monthlyTrigger: 'every_5_issues'   // 정식: 'monthly'
}
```

정식 전환 시 config만 바꾸면 되고, 스탯 산출·해설 생성 로직은 손대지 않는다.

> ⚠️ 압축 모드에서는 하루치 데이터로 한 주차를 채우므로 **스탯 변동 폭이 비현실적으로 클 수 있다.** 검증 목적상 오히려 유리하지만, 외부 데모 시 압축 모드임을 인지할 것.

#### 변동 해설 작성 규격

수치가 **하락한** 항목을 다룰 때 반드시 지킨다.

| 규칙 | 내용 |
|---|---|
| 원인 귀속 | **상황·맥락**에 귀속시킨다 (야근, 일정, 계절, 이사 등) |
| 금지 | 개인의 태도·의지·성의를 원인으로 지목하지 않는다 |
| 근거 필수 | 근거 데이터 없이 하락을 해석하지 않는다 |

**예시**

| 문장 | 판정 |
|---|---|
| "답장이 하루를 넘긴 날이 4회로 늘었습니다. 네 번 모두 평일 야근이 있던 날입니다." | ✅ 사실 + 외부 요인 귀속 |
| "답장에 소홀해졌습니다." | ❌ 태도를 문제 삼음 |
| "상대를 덜 챙긴 달이었습니다." | ❌ 판정 |

> 발행물 실물(Vol.01)의 "서영 · 멘탈 회복력 57 → 52" 항목이 이 규격의 기준 사례다.
> 수치 하락을 말하되 원인을 야근이라는 외부 사정으로 귀속시켰다.

### 17-4. 다정한 말들 (일간 / MVP는 월간)

#### 개념

채팅 중 다정했던 발화를 뽑아 압축(zip)해 보여주는 코너. **ONDOLOG의 창업 문제의식과 가장 직접 연결된다** — "다투는 채팅이 전날의 다정했던 채팅을 순식간에 덮어버린다"는 문제를 정면으로 해결하는 지면.

#### 발행 형태

| 단계 | 형태 |
|---|---|
| **MVP** | 월간 매거진 안에 **"이달의 다정한 말들"**로 포함 — 한 달치에서 선별 |
| **정식 운영** | **일간**으로 분리 — 어제 대화에서 선별해 매일 발행 |

선별 로직은 동일, **대상 기간만 config로 전환**(`daily` = 어제 / `monthly` = 지난 한 달).

#### 선별 로직 — 감정 노이즈 필터링

| 처리 | 내용 |
|---|---|
| 포함 | 다정함·배려·애정·유머가 담긴 발화 |
| **제외** | 다툼·비난·냉담한 발화 |
| 우선순위 | ① 감정 강도 ② 상대의 반응이 좋았던 것 ③ 평소와 다른 표현 |

> 이 필터링이 코너의 존재 이유다. 채팅 로그를 그대로 보여주면 카카오톡과 다를 게 없다. **덮인 것을 다시 꺼내주는 것**이 가치다.

#### 인용 방식 — 원문 + 출처 표기 + 담백한 맥락

**표기 형식**
```
— 2026.08.22 09:20, ○○의 대화 중
```

**지면 예시**
```
아침 출근길에 오간 대화

— 2026.08.22 09:20, 아침 대화 중
"오늘 비 온대. 우산 챙겼어?"
"응 챙겼어. 너도 감기 조심해"
```

**AI의 역할 범위**

| 허용 | 금지 |
|---|---|
| 상황·맥락을 담백하게 서술 | 발화에 대한 평가·해석 |
| 시간·정황 정리 | "정말 다정하시네요" 같은 감상 |
| 다정하고 따뜻한 문장을 **발췌**해 소개 | 점수 매기기, 칭찬, 훈수 |

> **AI는 편집자이지 평론가가 아니다.** 그 대화가 얼마나 좋았는지 말하는 순간 유저는 감시받는 기분을 느낀다.

#### 다툼만 있던 기간 처리

**발행 스킵.** 억지로 다정함을 만들어내지 않는다.

| 조건 | 동작 |
|---|---|
| 다정한 발화 없음 | 해당 기간 코너 미발행 |
| 지면 처리 | 다른 코너로 지면 채움 |

> 안 좋았던 시기에 억지로 "그래도 이런 말이 있었어요"를 들이미는 건 역효과다.

#### 지면 구성 (MVP 월간 버전)

| 요소 | 내용 |
|---|---|
| 헤드 | "이달의 다정한 말들" + 그 달 다정 지수 |
| 메인 인용 | 그 달 가장 다정했던 대화 2~3턴 |
| 맥락 | 언제, 어떤 상황이었는지 AI 한 줄 서술 |
| 서브 | 나머지 다정한 발화 4~6개를 작게 나열 |

### 17-5. 이달의 우리 (월간)

#### 개념

AI가 그 달의 **테마를 추출**해 소기사로 구성하는 코너. 다른 코너들이 정해진 형식을 채우는 구조라면, 이 코너는 **형식 자체가 매달 달라진다.**

#### 원재료 — 다른 코너의 원재료를 전부 사용

| 소스 | 활용 |
|---|---|
| 피드 데이트 기록 | 어디를 갔는지, 무엇을 했는지 |
| 채팅 로그 | 무슨 얘기를 많이 했는지 |
| 유저가 남긴 글·그림 | 감정의 흐름 |
| 연애리그 스탯 변동 | 관계의 변화 |
| 연애 온도 추이 | 한 달의 기복 |

#### 동작 구조

```
한 달치 전체 데이터 스캔
  → 반복되는 패턴·키워드·감정 흐름 추출
  → 그 달을 관통하는 테마 1개 선정
  → 테마를 여러 각도로 쪼개 소기사 작성
```

**테마 예시**

| 테마 | 소기사 구성 예 |
|---|---|
| "이사 준비의 한 달" | ① 집 보러 다닌 기록 ② 가구 얘기로 채워진 대화 ③ 예산 갈등과 화해 ④ 새 동네 첫 산책 |
| "바빴던 한 달" | ① 줄어든 만남 횟수 ② 늦은 밤 짧은 대화들 ③ 그래도 챙긴 순간 ④ 다음 달 계획 |
| "새로운 걸 많이 해본 달" | ① 처음 가본 장소 3곳 ② 새 취미 ③ 평소와 다른 대화 주제 ④ 변한 스탯 |

#### 지면 구성

| 순서 | 요소 |
|---|---|
| 1 | **테마 헤드라인** — 그 달을 한 문장으로 |
| 2 | **리드문** — 왜 이 테마가 뽑혔는지 담백하게 |
| 3 | **소기사 2~4편** — 각각 사진·인용·데이터를 곁들여 |
| 4 | **마무리** — 다음 달로 이어지는 한 줄 |

#### 데이터 부족 시 — 분량 축소

코너 자체는 유지하되 소기사 개수만 조정한다.

| 데이터량 | 소기사 개수 |
|---|---|
| 충분 | 4편 |
| 보통 | 3편 |
| 적음 | 2편 |
| 극히 적음 | 최소 2편 확보 (기간 확장해서라도) |

> 코너를 통째로 빼면 매거진 구성이 흔들리지만, 분량만 줄이면 지면은 유지된다.

#### 테마 톤 정책 — 부정적 테마 배제

| 처리 | 내용 |
|---|---|
| 테마 후보 제한 | **중립·긍정 테마만** 추출 대상 |
| 금지 | "멀어진 한 달", "다툼이 많았던 달" 등 관계를 부정적으로 규정하는 테마 |
| 대안 | 부정적 소재를 후보에서 제외하고 **다른 소재**로 테마를 잡음 (그달 갔던 장소, 나눈 대화 주제 등) |

> ⚠️ **중요한 구분**: 부정을 긍정으로 **포장**하는 게 아니라, 부정적 소재를 테마 후보에서 **제외**하고 다른 소재로 테마를 잡는 것이다. 포장은 유저가 금방 알아채고 거부감을 느낀다.

#### AI 역할 범위 (생성 비중이 가장 높은 코너 — 원칙 준수 특히 중요)

| 허용 | 금지 |
|---|---|
| 패턴을 발견하고 이름 붙이기 | 관계에 대한 평가 |
| 데이터를 근거로 서술 | "두 분 정말 잘 지내시네요" 류 감상 |
| 유저 원본(사진·대화·글)을 인용해 뒷받침 | 근거 없는 추측이나 각색 |

> 테마를 뽑는 건 AI의 일이지만, 그 테마를 증명하는 건 **유저의 원본 기록**이어야 한다.

### 17-6. 우리 사이 인터뷰 (주간)

#### 개념

**제3자가 두 사람을 인터뷰하는 형식.** 각자에게 같은 질문을 따로 던지고, **"상대가 뭐라고 답했을까"를 예측**하게 한 뒤, 실제 답과 나란히 싣는다.

**동력은 정답 맞히기가 아니라 어긋남이다.**

| 결과 | 반응 |
|---|---|
| 맞음 | "역시 알고 있었네" |
| 어긋남 | **"어? 그렇게 생각했다고?"** ← 대화를 만든다 |

썸원이 "질문에 각자 답하고 양쪽 완료 시 공개"로 검증한 구조에 **예측 레이어를 한 겹 더** 얹은 것이다.

#### 진행 구조

```
1. 주 초, 두 사람에게 같은 질문 4개가 도착
2. 각자 답한다
   ① 나의 답
   ② 상대는 뭐라고 답했을 것 같은가 (예측)
3. 양쪽이 모두 완료하면 공개
4. 주말 발행 주간 리포트에 지면으로 실린다
```

**양쪽 완료 전까지 공개하지 않는다.** 먼저 본 쪽이 답을 맞춰갈 수 있기 때문이다.

#### 질문 구성 — 고정 3 + AI 생성 1

| Q | 유형 | 출처 | 예시 |
|---|---|---|---|
| Q1 | 취향형 | 고정 풀 | "상대가 가장 좋아하는 계절은?" |
| Q2 | 관찰형 | 고정 풀 | "상대가 요즘 가장 신경 쓰는 일은?" |
| Q3 | 관계형 | 고정 풀 | "우리가 처음 만났을 때 상대의 첫인상은?" |
| Q4 | 맞춤형 | **AI 생성** | "그날 카페에서 상대가 뭘 시켰는지 기억나?" |

**Q4 생성 규칙**

| 규칙 | 내용 |
|---|---|
| 근거 필수 | 그 주 데이터에 실제로 존재하는 사건만 소재로 삼는다 |
| 예측 가능성 | 상대가 답할 수 있는 질문이어야 한다 (본인만 아는 정보 금지) |
| 판정 금지 | "왜 그랬을까?" 류의 추궁형 질문 금지 (Part 3-7) |
| 데이터 부족 시 | Q4를 생성하지 않고 **3문항으로 발행** |

Q4에만 근거를 표기해 유저가 왜 이 질문이 나왔는지 알 수 있게 한다.

#### 지면 구성

```
우 리  사 이  인 터 뷰                    8월 3주차
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Q1  상대가 가장 좋아하는 계절은?

    세준의 답            서영의 답
    가을                 여름

    세준의 예측          서영의 예측
    서영은 봄            세준은 가을

─────────────────────────────────────

Q4  그날 카페에서 상대가 뭘 시켰는지 기억나?
    8.19 연남동 OO카페

    ...

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
가장 크게 갈린 문항 — Q2
```

**정오 표시와 개수 집계를 하지 않는다.** "맞혔습니다/어긋났습니다"를 지면이 판정하면 "누가 더 잘 아는가"가 되어 한쪽이 불편해진다. 읽는 사람이 알아서 본다. 어긋남에 대한 대화가 지면 밖에서 일어나는 것이 이 코너의 목적이다.

#### 알림

| 시점 | 알림 |
|---|---|
| 질문 도착 | "이번 주 인터뷰가 왔어요" |
| 상대 완료 | "서영이 답했어요" |
| 마감 하루 전 | 리마인드 |
| 양쪽 완료 | "서로의 답을 볼 수 있어요" |

**주 1회 4문항을 유지한다.** 매일 1문항으로 쪼개면 참여율은 오르지만 채팅 탭과 역할이 겹친다. 주간 리포트라는 발행 리듬을 지키는 것이 제품 정체성에 맞다.

#### 데이터 부족 시

| 상황 | 처리 |
|---|---|
| 한쪽만 답변 | **미발행.** 다음 주로 이월 |
| 둘 다 미답변 | 코너 스킵 |
| 일부 문항만 | 완료된 문항만 게재 |

#### 스키마

```
interview_questions          -- 고정 풀 전용
  id, category(taste/observation/relation), text, active

interview_rounds
  id, couple_id, period_start, period_end,
  question_ids[],            -- 고정 풀 3개 참조
  generated_question jsonb,  -- Q4 (text, basis, source_ref) nullable
  status

interview_answers
  id, round_id, question_ref, user_id,
  own_answer, predicted_partner_answer, answered_at
```

**예측이 별도 컬럼**인 것이 이 코너의 핵심이다. 일반 Q&A와 구조가 다르다.

### 17-7. 오프라인 셋로그 (주간)

#### 개념

**데이트가 없던 시간, 각자의 하루를 사진으로 남긴다.**

다른 코너는 전부 "함께한 것"을 다루는데 이 코너만 "따로 있던 시간"을 다룬다. 커플이 함께 있는 시간은 일주일에 몇 시간뿐이고 나머지는 각자 살아가는데, 그 시간이 앱에서 통째로 빠져 있기 때문이다.

> "오늘 뭐 했어?" → "그냥 일했지"
> 실제로는 그냥 일한 게 아니다. 말로 옮기기 귀찮을 뿐이다.

#### 입력 — 매거진 제작 탭이 유일한 창구

```
푸시 알림 (매일 정해진 시각)
  "데이트가 없는 오늘, 세준님은 무엇을 하셨나요?"
  ↓ 탭
매거진 제작 탭 → 오프라인 셋로그 → 오늘 기록하기
  ↓
사진 선택 + 한 문장
  ↓
저장 (EXIF로 시간·장소 자동 추출)
```

**피드 탭(자동 인식)과 경로가 완전히 분리된다.** 이 경로로 들어온 사진은 정의상 셋로그다.

**자동 판정을 쓰지 않는 이유**

초안에서는 얼굴 인식으로 데이트/셋로그를 자동 구분하려 했으나 폐기했다.

| 문제 | 내용 |
|---|---|
| 데이트에도 얼굴이 안 나온다 | 풍경·음식 사진이 대부분 |
| 혼자일 때도 얼굴이 나온다 | 셀카 |
| 오분류의 원인을 유저가 알 수 없다 | 왜 이 사진이 저기 갔는지 설명 불가 |

**자동 판정이 애매한 곳에서는 유저에게 맡긴다.** 얼굴 인식은 "우리 커플 사진인가"를 거르는 도구지 "데이트인가 아닌가"를 판정하는 도구가 아니다.

| 항목 | 필수 | 처리 |
|---|---|---|
| 사진 | 1장 이상 | 유저 선택 |
| 설명 | 한 문장 | 유저 입력 |
| 시간 | — | **EXIF 자동** |
| 장소 | — | **EXIF 자동**, 수정 가능 |

**30초 안에 끝나야 한다.** 태그 선택도 컨디션 입력도 없다.

**알림**: 매일 정해진 시각(기본 밤 9시, 설정 변경 가능). **조건을 걸지 않는다** — 데이트한 날에도 따로 있던 시간은 있고, 판정 로직도 사라진다. 무시하는 건 부담이 없다.

#### 지면 구성 — 그 주의 대표적인 하루 1일

```
오 프 라 인  셋 로 그                8월 20일 목요일
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

        세준                    서영

08:20   ┌──────┐
        │ 사진  │
        └──────┘
        지하철에서 책 읽는 중

                                09:15   ┌──────┐
                                        │ 사진  │
                                        └──────┘
                                        출근길 커피

12:40   ┌──────┐
        │ 사진  │
        └──────┘
        회사 근처 점심

                                19:30   ┌──────┐
                                        │ 사진  │
                                        └──────┘
                                        운동 끝나고

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
같은 시간대 — 12:40 세준 점심 · 12:55 서영 점심
```

**시간축이 세로로 흐르고 좌우가 두 사람이다**(Part 9-1 좌우 대칭 원칙). 시간이 겹치면 나란히, 안 겹치면 계단처럼 어긋난다. **이 어긋남 자체가 "따로 살고 있다"는 시각 언어**가 된다.

7일치를 다 실으면 지면이 표가 되고 사진이 작아져 화보 느낌이 사라진다. **한 날을 제대로 보여준다.**

#### 대표 하루 선별

| 우선순위 | 기준 | 이유 |
|---|---|---|
| 1 | **양쪽 다 기록이 있는 날** | 좌우 대칭이 성립해야 지면이 산다 |
| 2 | 사진 총 수가 많은 날 | 화보로 채워진다 |
| 3 | 시간대가 겹치는 순간이 있는 날 | 이 코너만의 재미 지점 |
| 4 | 시간 폭이 넓은 날 (아침~밤) | 하루가 온전히 보인다 |

#### AI의 역할

| 허용 | 금지 |
|---|---|
| EXIF로 시간·장소 자동 분류 | 사진 내용을 해석해 서술 추가 |
| 시간순 배치, 대표 하루 선별 | 유저 설명을 다듬거나 대체 |
| 겹친 시간대 짚기 | "만남이 적었습니다" 류 판정 |

**잉크 위계상 담묵.** 유저 사진과 한 줄이 전부다.

#### 데이터 부족 시

| 상황 | 처리 |
|---|---|
| 한쪽만 기록 | **한쪽 열만 채워 발행.** 빈 열은 조용히 비운다 |
| 둘 다 없음 | 코너 스킵 |

한쪽만으로도 발행하는 것이 인터뷰와 다른 점이다. 인터뷰는 예측 비교라 양쪽이 필요하지만 셋로그는 각자의 기록이다.

> 빈 열이 "안 했다"는 지적으로 읽히지 않게 한다. 강조하지 않고 조용히 비워둔다.

#### 스키마

`data_entries`를 재사용하되 **명시적 타입으로 구분**한다.

| 필드 | 셋로그에서 |
|---|---|
| `entry_type` | `'setlog'` |
| `date_id` | 항상 null |
| `captured_at` / `lat` / `lng` | EXIF 자동 |
| `text_content` | 한 문장 설명 |

**`date_id` 유무로 추론하지 않는다.** 추론이 아니라 선언이라야 모호함이 없다.

### 17-8. 특별 게스트 · 무물 (월간, 기념일 한정)

#### 개념

기념일이 있는 달에, 두 사람을 아는 지인들에게 링크를 보내 메시지를 받아 지면에 싣는다.

**ONDOLOG에서 유일하게 외부인이 등장하는 지면이자, 유일한 바이럴 장치다.** 링크를 받은 사람이 앱을 알게 된다.

#### 발행 조건 — 기념일이 있는 달에만

| 기념일 | 판정 |
|---|---|
| 100일 단위 | 100·200·300… |
| 연 단위 | 1주년·2주년… |
| 생일 | 양쪽 각각 |

해당 없는 달은 코너가 나오지 않는다. 상시 발행하면 지인에게 매달 연락하는 셈이라 부담스럽다.

#### 링크 생성 — 해당 달에 상시 노출

```
특별 게스트                        대기 중  →
8월 27일 · 500일   링크 만들기
```

기념일과 남은 날짜를 함께 표시해 왜 지금 이 코너가 열렸는지 알 수 있게 한다.

#### 질문 구성

| 유형 | 개수 | 예시 |
|---|---|---|
| 고정 | 2 | "두 사람을 처음 봤을 때 어땠나요?" / "두 사람 하면 떠오르는 장면이 있나요?" |
| 커플 작성 | 1 | 자유 |

**고정 질문 설계 원칙**: 답하는 사람이 부담 없이 쓸 수 있어야 한다. "두 사람의 문제점은?" 같은 질문은 넣지 않는다. Part 3-7 판정 금지 원칙이 외부인에게도 적용된다.

커플 작성 시 안내를 노출한다 — *"답하는 분이 부담 없이 쓸 수 있는 질문이 좋습니다."*

#### 답변자 표시 — 닉네임

링크를 연 사람이 **직접 닉네임을 설정**한다.

```
"세준이가 저렇게 웃는 걸 처음 봤습니다"
                              — 회사 동기 민수
```

| 항목 | 내용 |
|---|---|
| 설정 | 답변자가 직접 입력 (20자 이내) |
| 검증 | 없음 (본명이든 별명이든 자유) |

> 닉네임을 걸면 답변이 "관찰"보다 "덕담"에 가까워진다. 기념일 발행이라는 성격과 합치면 오히려 이쪽이 맞다. 이 코너는 **지인들의 방명록**에 가깝다.

#### 승인 — 앱에서 전부 보고, 지면에는 골라 싣기

```
답변 수집
  ↓
AI 1차 필터 (명백한 욕설·혐오 자동 제외)
  ↓
앱에서 전체 목록 열람 — 승인 여부와 무관하게 다 볼 수 있다
  ↓
양쪽 모두 "싣자"를 누른 답변만 지면에 게재
```

| 규칙 | 내용 |
|---|---|
| 기본값 | **미승인.** 아무것도 안 하면 안 실린다 |
| 열람 | 승인 안 한 답변도 앱에서는 계속 볼 수 있다 |
| **양쪽 동의** | 한 사람만 승인하면 게재되지 않는다 |
| 거부 | 사유 불필요 |
| 전부 미승인 | 코너 스킵 |

**"모든 답변은 앱에서 보고, 지면에는 고른 것만"이 핵심이다.** 받은 마음은 다 확인하되 책에 남길 건 두 사람이 정한다.

> 양쪽 동의를 요구하는 이유: 한 사람은 괜찮은데 다른 사람은 불편한 답변이 있을 수 있다. 한쪽만 승인하면 상대의 불편을 대신 판단하는 셈이다.
> AI 필터를 1차로 두되 최종 판단은 사람이 한다. AI가 걸러내지 못하는 맥락적 불쾌함(둘만 아는 과거를 건드리는 등)이 있다.

#### 링크 보안

| 항목 | 값 |
|---|---|
| 유효 기간 | 7일 |
| 응답 수 상한 | 10명 |
| 앱 설치 | **불필요** (웹 페이지) |
| 즉시 무효화 | 커플이 언제든 가능 |

**즉시 무효화가 중요하다.** 링크가 의도치 않은 곳으로 퍼졌을 때 유일한 대응 수단이다.

#### 지면 구성

```
특 별  게 스 트                    2026년 8월 · 500일
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

두 사람을 처음 봤을 때 어땠나요?

  "잘 어울린다는 생각보다
   되게 편해 보인다는 생각이 먼저 들었어요"
                                — 대학동기 지현

  "세준이가 저렇게 웃는 걸 처음 봤습니다"
                                — 회사 동기 민수

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
이번 호에는 네 분이 답해주셨습니다
```

**잉크 위계상 담묵.** 외부인 원문 그대로이고 AI는 배치만 한다.

#### 스키마

```
guest_invites
  id, couple_id, token,
  milestone_type, milestone_date,      -- 어떤 기념일로 열렸는지
  question_ids[], custom_question,
  expires_at, max_responses, revoked_at, created_at

guest_responses
  id, invite_id, question_ref,
  nickname, answer_text,
  ai_filtered boolean,
  approved_by_a boolean default false,
  approved_by_b boolean default false,
  responded_at
```

#### 미해결 — 웹 페이지 필요

이 코너는 **앱 밖에 웹 페이지가 하나 필요하다.** 링크를 받은 사람이 앱 설치 없이 답변하는 화면이다. 지금까지 ONDOLOG는 앱 전용이었으므로 여기서 처음 웹이 등장한다. Supabase Edge Function 서빙 또는 별도 호스팅이 필요하며 **Phase 2 확장 시점에 다시 다룬다.**

### 17-9. 얼렁뚱땅 어림짐작 (월간)

#### 개념

성격 벡터와 실제 기록을 결합해 연애 상황에서의 "찰나의 반응"을 재미 위주로 추정한다.

**정확한 진단이 아니라 어림짐작임을 코너명 자체로 고지한다.** 연애 DNA(진지)와 톤을 의도적으로 분리한다.

| 항목 | 값 |
|---|---|
| 지면 | 가십·운세면 (후반부) |
| 역할 | 연애 DNA의 무게감을 상쇄하는 엔딩 코너 |
| 잉크 위계 | **세이지/샴페인** — 계산된 지표 |

#### 8개 항목

| # | 항목 | 입력 | 출력 |
|---|---|---|---|
| 1 | 먼저 고백했을 확률 | 외향성 E + 애니어그램 주장형(3·7·8) + 스턴버그 열정 | 확률 배지 |
| 2 | 갈등 회피 지수 | 우호성 A + 애착 회피축(Q5) + 애니어그램 후퇴형(4·5·9) | 확률 배지 |
| 3 | 기념일 챙기는 정도 | 성실성 C + 스턴버그 헌신 + MBTI J/P | 확률 배지 |
| 4 | 답장 속도 | 신경성 N + 성실성 C + **실제 채팅 응답속도** | 좌우 비교 |
| 5 | 먼저 말을 거는 쪽 | **실제 채팅 대화 시작 횟수** | 게이지 |
| 6 | 이모지를 더 쓰는 쪽 | **실제 채팅** | 게이지 |
| 7 | 가장 말이 많았던 날 | **실제 채팅** | 날짜 + 한 줄 |
| 8 | 이달의 어림짐작 | 성격 벡터 + 주제 풀 | 주제별 상이 |

**5분 인터뷰 기반이던 기존 입력 변수를 5문항 시스템으로 재매핑했다.** 4번은 기존에 설문 응답으로 추정하던 것을 **실제 채팅 로그 실측**으로 바꿨다.

**폐기된 항목**: "서운함 흑역사 데이터 저장소" — 한 사람의 성향을 부정적으로 지목해 Part 3-7과 충돌한다. 면책 문구로 덮는 것은 해법이 아니다.

#### 주체 명시 규칙

커플이 함께 읽는 지면이므로 **"누가"를 반드시 밝힌다.**

```
세준님이 먼저 고백했을 확률 73%
```

50% 미만일 때는 뒤집는 게 아니라 **주체를 바꿔서** 표현한다.

```
"세준님이 먼저 고백했을 확률 27%"  →  "서영님이 먼저 고백했을 확률 73%"
```

#### 7. 가장 말이 많았던 날

```
8월 14일

그날은 이사 얘기가 오갔습니다
```

| 규칙 | 내용 |
|---|---|
| 분량 | 한 줄, 20자 내외 |
| 형식 | "그날은 OO 얘기가 오갔습니다" |
| 근거 | 그날 대화의 반복 키워드 |
| 판정 금지 | "다퉜습니다" 같은 서술 금지 |
| 추출 불가 시 | 날짜만 표시하고 한 줄 생략 |

> 다툼이 있던 날이 대화량 1위일 수 있다. 그때는 주제 한 줄을 생략하고 날짜만 둔다. 억지로 좋게 포장하지도, 부정적으로 쓰지도 않는다.

**이 항목만 LLM 호출이 필요하다.** 나머지 7개는 규칙 기반이다. 하루치 대화만 보므로 비용은 미미하다.

#### 8. 이달의 어림짐작 — 주제 풀

**매달 하나씩 다른 주제가 나온다.** 12개 주제로 1년 동안 겹치지 않는다.

| # | 주제 | 입력 | 출력 예 |
|---|---|---|---|
| 1 | 여행 계획을 세운다면 | MBTI J/P + 성실성 | "세준님이 숙소를 먼저 정할 확률 89%" |
| 2 | 메뉴 고르는 시간 | 개방성 + 성실성 | "세준님 2분 · 서영님 11분" |
| 3 | 영화관에서 앉는 자리 | 외향성 + 개방성 | "세준님 가운데 뒷줄 · 서영님 통로 쪽" |
| 4 | 짐 싸는 시점 | 성실성 + MBTI J/P | "세준님 3일 전 · 서영님 전날 밤" |
| 5 | 길 잃었을 때 | 애니어그램 주장형 + 외향성 | "먼저 지도를 켤 확률 — 세준님 71%" |
| 6 | 노래방에서 | 외향성 + 애니어그램 | "먼저 마이크를 잡는 쪽 — 서영님" |
| 7 | 사진 찍을 때 | 개방성 + 외향성 | "포즈를 정하는 쪽 — 세준님" |
| 8 | 장 보러 가면 | 성실성 + 개방성 | "목록대로 살 확률 — 세준님 92%" |
| 9 | 리모컨을 쥐는 쪽 | 애니어그램 주장형 + 외향성 | 게이지 |
| 10 | 새 카페에 가면 | 개방성 + 신경성 | "메뉴판을 오래 보는 쪽 — 서영님" |
| 11 | 늦잠 잔 아침 | 신경성 + 성실성 | "먼저 일어나는 쪽 — 세준님" |
| 12 | 짐 정리 방식 | 성실성 + 개방성 | "세준님 분류형 · 서영님 몰아넣기형" |

**선택 로직 — 랜덤이 아니라 결정론적 선택**

```typescript
// src/engine/roughGuess.ts — 순수 함수
function selectMonthlyTopic(coupleId: string, period: string): Topic {
  const seed = hashString(coupleId + period);
  return TOPIC_POOL[seed % TOPIC_POOL.length];
}
```

| 규칙 | 내용 |
|---|---|
| 결정론 | 같은 커플·같은 달 → 항상 같은 주제 (절대 규칙 2 준수) |
| 커플마다 다름 | `couple_id`가 시드에 포함되어 커플별로 다른 주제가 나온다 |
| 재생성 안전 | 코너를 다시 만들어도 결과 동일 |

> ⚠️ 풀에 주제를 추가하면 `% length`가 바뀌어 과거 호를 재생성할 때 다른 주제가 나온다. 발행된 코너는 `corners.content` 스냅샷이라 안전하지만, 이 사실을 인지하고 있어야 한다.
