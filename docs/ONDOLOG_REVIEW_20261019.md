## 3. 어긋난 것 — 무거운 순서

### 3-1. 제품의 핵심 가설이 한 번도 시험되지 않았다

MASTER 7-3은 "첫 호 발행이 퍼널의 병목이고, **코너 생성 완성도가 최우선**"이라고 한다. 6-7 ①은 "한국어 서사 품질은
**개발 착수 시** 실제 생성으로 비교해 확정한다"고 한다. 그런데 기록상 실제 모델 호출은 0회다.

방어층은 정교하지만 **방어 대상(실제 출력)을 본 적이 없다.** 출력이 "담백하되 평가하지 않는" 톤에 못 미치면
프롬프트와 LLM 출력 스키마를 바꿔야 하고, 그 위의 검증·시험도 같이 고쳐야 한다. 늦게 알수록 고칠 양이 커진다.

### 3-2. 데이터가 들어올 길이 채팅뿐이다

앱에 사진·데이트 기록을 넣는 경로가 없다. 데이트 아카이브(17-1)와 이달의 우리의 사진 재료는 **Phase 6 얼굴 인식
자동 정리에만** 묶여 있고, Phase 6은 폰을 기다리고 있다.

그런데 MASTER 3-4의 MVP 핵심 문장은 **"커플이 사진과 메모를 올리면"**이다. 수동 업로드만으로 성립한다. 9-4도 수동
업로드를 명시하고("자동 인식 + 수동 업로드"), 디자인 v5는 이미 그 화면을 그려 두었다(E10 사진 직접 추가, E11 데이트 기록 쓰기).

### 3-3. 얼굴 인식 1차 라이브러리를 npm에서 찾을 수 없다

MASTER 9-4가 1차로 채택한 `react-native-expo-facial-recognition`은 **npm 레지스트리에 없다**(2026-10-19
`npm view` 결과 404). Phase 6의 전제가 무너진다. 남은 길은 9-4가 2차 후보로 둔 **커스텀 네이티브 모듈**(탐지는
ML Kit/Vision, 임베딩은 ONNX·TFLite 모델)뿐이고, 이건 네이티브 작업이 크다. 이 위험이 MVP 임계 경로에 있으면 출시
전체가 여기에 묶인다.

### 3-4. PDF 렌더링이 돌 곳이 없다

SCHEMA §11-4는 "PDF 렌더링은 Playwright가 필요하므로 **Edge Function 스케줄러**로 실행한다"고 적었다. 하지만
**Supabase Edge Function은 그 안에서 Chromium을 띄울 수 없다.** Supabase 공식 예제도 함수 크기 제한 때문에 원격 브라우저
서비스에 접속하는 방식을 쓴다. 렌더링 실행 위치는 아직 결정되지 않았다.

반대로 좋은 소식도 있다. **6테마 19면 조판은 디자인 파트가 이미 Chromium으로 뽑아 두었다**
(`docs/design/magazine/*.pdf`, A4 19면 6종). 다만 그 HTML 템플릿 소스는 저장소 밖에 있다.

### 3-5. MVP 노출 지표 셋이 '실사용 데이터'를 기다리는 계수에 막혀 있다

| 계수 | 막고 있는 것 | 해소 조건(문서) |
|---|---|---|
| `temperature.activityScore` | **메인 탭 온도 히어로** — 지금은 "아직 온도를 잴 기록이 없어요"로 고정 | 실사용 데이터 |
| `dnaScore.chatDelta` | **연애 DNA 코너** — 17-0이 발행 대상에서 제외 | 실사용 채팅 |
| `leagueStats.shrinkage` | **연애리그 코너** — 17-0이 발행 대상에서 제외 | 채팅 사후확률의 관측 분산 |

실사용 데이터는 앱이 돌아야 생긴다. 그러니 **순환**이다. 이대로 가면 MVP 잡지는 3코너가 되고, 13-5-2의 "MVP 5개
코너"는 달성할 수 없다. "근거 없는 값을 지어내지 않는다"는 원칙은 맞다. 다만 그 원칙에는 **"PM이 v0 값을 결정으로
확정하고, 버전을 남기고, 베타 데이터로 고친다"는 짝**이 있어야 했다. 그 짝이 빠져 있었다.

### 3-6. '완료'가 '동작 확인'을 뜻하지 않는다

Phase 3~5는 ✅이지만 **실기기 E2E가 한 번도 없다.**
- 카카오 로그인은 미검증이다. 구글·애플은 화면에서 "준비 중"으로 막혀 있다.
- `.env` anon key가 자리표시자라는 기록(HANDOFF "여전히 필요한 처리" 2번)은 해소 여부가 확인되지 않았다.

**로그인이 막히면 그 뒤의 모든 화면이 막힌다.** ROADMAP이 "최대 리스크"로 적어 둔 그대로다.

### 3-7. 발행 주기 결정이 서로 어긋난다

| 출처 | 내용 |
|---|---|
| MASTER 9-5 · 13-5-1 | MVP는 **매일 발행**으로 파이프라인을 검증한다 |
| MASTER r52 §17-0-10-A | 발행은 **유저 확인**이다. 매일 확인을 받는 UX는 성립하지 않는다 |
| 디자인 v5 | 전 화면이 **월간** 전제다 |

매일 발행은 원래 "한 달을 기다리지 않고 검증하기" 위한 장치였다. 운영자가 원하는 기간으로 언제든 생성할 수 있으면
같은 목적을 매일 발행 없이 달성한다.

### 3-8. 앱 UI 전체가 교체 예정인데, 옛 디자인 위에 계속 짓고 있다

디자인 v5는 온보딩을 포함해 101화면을 다시 그렸다. 현재 앱 화면은 전부 v1 종이 톤이다. 토큰 호환층은 디자인 세션의
매핑표를 기다리며 멈춰 있다. **지금 옛 디자인으로 새 화면을 만들면 그대로 다시 만들어야 한다.**

### 3-9. 개발 환경이 저장소만으로 재현되지 않는다

스냅샷을 새로 설치해 확인했다.
- `npm install --legacy-peer-deps`(CLAUDE.md 알려진 이슈와 HANDOFF에 적힌 설치 방식)로 깨끗이 설치하면 **jest가 아예 시작하지 않는다.**
  `jest-expo`·`@testing-library/react-native`의 피어 의존인 **`@react-native/jest-preset`, `test-renderer`가
  `package.json`에 없기** 때문이다.
- 둘을 lock의 버전(0.86.2, 1.2.0)으로 넣으면 **tsc 0/0, jest 986·49가 그대로 재현된다.**

HANDOFF의 "현재 node_modules는 lock으로 재현 불가"와 같은 뿌리다. PC가 고장 나면 개발 환경을 다시 세울 수 없다.
GitHub `main`도 10-09에 멈춰 있어 **백업 공백**이 있다.

### 3-10. 운영 비용이 산출을 압도한다 — PM 책임

1인 창업자가 PM ↔ PE ↔ 메인 세션 ↔ 서브에이전트 사이를 **손으로 중계**한다. 그 위에서 PM은 테스트 위치·주석 문구·
파일 경계 같은 **내부 구현 결정까지** 내렸다. 그 결과가 MASTER 56회 개정이고, 상태 파일 정리만으로 지시서가 여러 건
나왔다(`24-`·`25-`·`43-`). 지시서 하나가 시연 가능한 결과 하나와 연결되지 않았다. **이 순서를 만든 것은 PM이다.**
